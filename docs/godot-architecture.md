# Устройство godot-части порта

Подчинено [docs/principles.md](principles.md): поведение как в оригинале, устройство — по современным
игровым стандартам. Здесь описано, как разложена сторона Godot и почему именно так. Правила движка,
проверенные прогоном, — в [docs/godot-notes.md](godot-notes.md); формат модов — в [docs/modding.md](modding.md).

## Раскладка

```text
godot/                     проект Godot (res://) — только представление
  project.godot
  D2.Godot.csproj
  autoload/                автозагрузки: то, что живёт весь сеанс и не привязано к сцене
    GameData.cs
  scenes/
    boot/                  главная сцена: данные игры импортированы? нет — окно импорта (docs/publishing.md), да — меню
      Boot.tscn  Boot.cs  GodotImageEncoder.cs
    ui/                    экраны интерфейса из данных
      UiFlow.tscn  UiFlowView.cs                        игра по графу экранов (после Boot)
      UiScreen.tscn  UiScreenView.cs  .Input.cs  .Content.cs  один экран; им же проверяются экраны
    map/                   экран карты
      MapScreen.tscn  MapScreen.cs          весь экран: DLG_ISO_VIEW + карта + панели + мини-карта
      MapView.tscn  MapView.cs  .Input.cs   вид карты: земля кусками, объекты, выбор, путь, ход
      MapObjects.cs  MiniMapView.cs  MapSource.cs  GroundArt.cs

src/                       код вне движка (.NET, тестируется без Godot)
  D2.Rules/                правила игры: формулы, очередь ходов, ИИ
  D2.Data/                 данные и логика интерфейса: Ui/, Menu/, Game/, Gfx/, Content/, Corpus/, Dbf/, Map/, Sg/
```

### Почему скрипт лежит рядом со сценой, а не в общем `scripts/`

У каждой сцены здесь ровно один класс скрипта, и меняются они всегда вместе (большой класс делится
на `partial`-файлы рядом: `UiScreenView.cs` — отрисовка, `UiScreenView.Input.cs` — ввод). Параллельное дерево `scripts/`
удвоило бы навигацию и дало бы третье место, где путь может разойтись с `.tscn` (после `ext_resource`
и `.uid`). Папка на сцену — это ещё и готовое место для её ресурсов, когда они появятся.

### Имена

- каталоги — строчными, одним словом (`scenes/ui`, `autoload`); разделов по типу узла (`sprites/`,
  `controls/`) не заводим — раздел означает часть игры;
- сцена и её скрипт названы одинаково и в `PascalCase`, имя файла совпадает с именем класса C#
  (`UiScreen.tscn` ↔ `UiScreenView.cs` — исключение осознанное: сцена про экран, скрипт про его отрисовку);
- в C# — обычные соглашения .NET, без венгерской записи и без приставок из GDScript;
- имена в данных — по смыслу, а не по кодам оригинала (`UiKind.TextList`, а не `TLBOX`), см.
  [principles.md](principles.md). Исключение — идентификаторы, по которым мод опознаёт сущность
  (`DLG_OPTIONS`, `_PG0250IX`): они пришли из игры и должны оставаться устойчивыми.

### Почему в `godot/` нет игровой логики

`godot/` — слой представления. Правила (`D2.Rules`) и чтение данных (`D2.Data`) — обычные проекты .NET,
подключённые `ProjectReference` из `D2.Godot.csproj`. Отсюда два следствия, ради которых это и сделано:
их покрывает `dotnet test` без движка вообще (в том числе харнессы С1/С2 против журналов зонда), и та же
логика годится для импортёров и инструментов. Сцена умеет только строить узлы и печатать числа.

Практическое правило: если код можно проверить без окна — ему место в `src/`, а не в `godot/`.

### Живые элементы экрана

Состояние экрана — `UiScreenState` (`src/D2.Data/Ui/UiScreenState.cs`): что под мышью, что нажато,
отключено, отмечено, значения счётчиков, выбор и прокрутка списков. Ввод он принимает в координатах
`Design` и отдаёт события (`UiClicked`, `UiToggled`, `UiGroupChanged`, `UiSpinChanged`, `UiListSelected`,
`UiListConfirmed`) и кадр каждого элемента (`Frame`). Сцена (`UiScreenView.Input.cs`) переводит события
Godot в эти координаты и виртуальные коды клавиш Windows (как в `Hotkeys` данных) и меняет текстуры —
решений в ней нет. Модель состояний — из реверса тулсета (`tools/d2probe/mss32/include`: `button.h`,
`togglebutton.h`, `radiobuttoninterf.h`, `spinbuttoninterf.h`, `listbox.h`); что в заголовках не описано,
выбрано по обычаю Windows и перечислено в комментарии класса — это сверяется с игрой.

### Логика экранов

Что экран показывает и что разрешает — `IScreenLogic` (`src/D2.Data/Menu`): наполняет экран при открытии
(`Open`), отвечает на события (`Handle`) и решает, пускать ли переход по графу (`Allows`). Пишет она только
в `UiScreenState` (тексты, кадры, фон, ролики, пункты списков) и в общий выбор игрока `NewGameSetup`; сцена
(`UiScreenView.Content.cs`) по `UiScreenState.Revision` перерисовывает изменившееся. Экран без логики
показывается по разметке. Новая логика — новый класс и строка в `MenuLogic.For`; сцену трогать не нужно.

### Где живёт содержимое игры

Данные **не** внутри `res://`. Базовый набор — `data/` в корне репозитория, графика — `assets/`
(вне git, пересобирается `tools/ui-assets/build_ui_assets.py`), моды — `mods/` и `user://mods`.

Причина ровно одна и она практическая: импортёры (`tools/UiImport`, `tools/ui-assets`) и тесты .NET
читают те же файлы, что и игра, ничего не зная про `res://`. Класть их в проект Godot значило бы либо
дублировать, либо тянуть путь `res://` в инструменты. Цена решения — сцена разбирает путь сама
(`ProjectSettings.GlobalizePath("res://") + ".."`), и делает это одно место: `GameData`.

## Как сцена находит данные

Через автозагрузку `GameData` (`godot/autoload/GameData.cs`) — единственную точку, где сцены берут
содержимое:

```csharp
var content = GameData.Content;                 // экраны и кадры, базовые + моды
var screen = content.Screens.First(s => s.Id == id);
string png = UiAssets.PathOf(asset, GameData.UiAssetsRoot);
```

Сама сборка слоёв — в `src/D2.Data/Content/GameContent.cs`: обычный C#, без ссылки на Godot, поэтому
она проверяется в `dotnet test` (`src/D2.Data.Tests/GameContentTests.cs`). В автозагрузке остаётся
только то, что без движка не сделать: разбор `res://`/`user://` и аргументы запуска.

Загрузка ленивая. `_Ready` читает лишь `mod.json` (дёшево) и печатает строку `mods: …` при **каждом**
запуске любой сцены — по журналу всегда видно, какие слои были включены; `mods: -` значит «ни одного»,
а не «строку забыли». Экраны и кадры читаются при первом обращении к `GameData.Content`, так что
`AnimTest` не падает от отсутствия `data/ui`.

Аргументы после `--`:

| Аргумент | Что делает |
| --- | --- |
| *(ничего)* | моды из `mods/` рядом с репозиторием и из `user://mods` |
| `--no-mods` | только базовый набор; так гоняются проверки |
| `--mods <каталог>` | вместо умолчаний один свой корень (путь от `godot/`) |

## Где подключается слой правил

`D2.Rules` в сцены не встраивается — сцена получает уже посчитанное состояние. В `BattleReplay` это
видно буквально: `RulesLoader.Load(globals)` + `CorpusBattleLoader` дают `BattleState`, а ходы берутся
из журнала (`ReplayTurns`), сцена только раскладывает узлы и двигает подписи. Когда появится живой бой,
на месте `ReplayTurns` окажется движок правил из `D2.Rules` — точка подключения та же, сцена не меняется.

Точка расширения для содержимого — данные плюс, если нужно, реализация интерфейса в `D2.Rules`;
править `switch` в сцене не требуется никогда.

## Настройки проекта

Всё, что стоит в `godot/project.godot`, и зачем:

| Настройка | Значение | Зачем |
| --- | --- | --- |
| `application/run/main_scene` | `res://scenes/boot/Boot.tscn` | главная сцена — проверка импорта данных игры (нет — окно импорта, `docs/publishing.md`; команда разработчика `--import`), затем игра по графу экранов `res://scenes/ui/UiFlow.tscn`; одиночный экран и стенды запускаются явным путём |
| `autoload/GameData` | `*res://autoload/GameData.cs` | содержимое и список модов доступны любой сцене; звёздочка — узел добавляется в дерево |
| `rendering/textures/canvas_textures/default_texture_filter` | `0` (Nearest) | **условие численной сверки**, не косметика: с линейным фильтром увеличенный спрайт смешивает цвет с соседними выбитыми пикселями, и чистый зелёный читается со снимка как `(0.035, 0.808, 0.035)` вместо `(0, 1, 0)` ([godot-notes.md](godot-notes.md)). Настройкой проекта, а не строкой в каждой сцене: спрайты наследуют фильтр по умолчанию |
| `display/window/size/viewport_width` / `_height` | `1280` / `720` | базовый размер (с 20.09, e8d1378): экраны игры нарисованы под 800×600 (координаты элементов в данных — в нём) и вписываются по центру, панель карты помещается целиком |
| `display/window/stretch/mode` | `canvas_items` | масштабируется содержимое канвы, а не растягивается готовый кадр — пиксельная графика при увеличении окна остаётся резкой. В игре (`UiFlow`) с 11.10 это действует только в режиме показа `nearest`: в режимах `sharp` (по умолчанию) и `integer` показ (`ScreenStage`) выключает растяжение корня кодом, рисует экраны в свой буфер с целым масштабом и кладёт буфер в окно сам (поле `Scaling` в `user://settings.json`, ключ `--scale`; `docs/ui-text.md`) |
| `display/window/stretch/aspect` | `expand` | вьюпорт растёт вместе с окном, движок не режет его до 800×600. Нужно потому, что каждый экран несёт свой `Design` и масштабируется сам (`UiScreenView.Rescale`), а `UiAnchor` в данных прямо обещает элементам разъехаться по краям, когда окно шире. `keep` это обещание закрыл бы |
| `display/window/size/window_width_override` / `_height_override` | `1280` / `720` | окно открывается базового размера |
| `dotnet/project/assembly_name` | `D2.Godot` | имя сборки, по нему движок находит классы сцен |

## Как гоняются проверки

Без человека и без глаз — каждая печатает числа и возвращает код:

```bash
dotnet build godot/D2.Godot.csproj      # сначала C#: без этого движок берёт старую сборку из godot/.godot/mono/
dotnet test                             # правила, данные, слои модов — без движка
python tools/ui-render-check.py         # ~50 проверок в headless: экраны, ввод, граф, карта, бой, ход ИИ; итог «ОК» или «ПРОВАЛ: n из N»
```

Сцены запускаются явным путём, аргументы сцены — после `--`:

```bash
"C:/Tools/bin/godot.cmd" --headless --path godot res://scenes/dev/AnimTest.tscn        # frames: 16
"C:/Tools/bin/godot.cmd" --headless --path godot res://scenes/battle/BattleReplay.tscn # turns: 7
"C:/Tools/bin/godot.cmd" --headless --path godot res://scenes/ui/UiScreen.tscn -- --screen DLG_OPTIONS --png ../.cache/x.png
"C:/Tools/bin/godot.cmd" --headless --path godot res://scenes/ui/UiScreen.tscn -- --screen DLG_LOAD_GAME --items TLBOX_GAME_LIST=30 --input "click 60,130; key 40; key 13"
```

Два правила из [godot-notes.md](godot-notes.md), от которых зависит устройство проверок:

- **снимок вьюпорта в headless не берётся** — драйвер отрисовки пустой, `GetImage()` возвращает `null`.
  Поэтому `UiScreenView` в headless складывает кадры в `Image` на стороне процессора и считает доли
  пикселей по ней, а не по экрану;
- **необработанное исключение C# не роняет процесс** — движок пишет ошибку и крутит цикл дальше. Значит
  успех обязан быть явным: строка с числами плюс `GetTree().Quit(код)`, а запуск — под таймаутом.

Проверка `ui-render-check.py` гоняется с `--no-mods`: она отвечает за базовый набор данных, а не за то,
что лежит в `mods/`.

## Чего здесь нарочно нет

Ни шины событий, ни слоя сервисов. Переходы между экранами живут в `UiFlowView` (узел-хозяин стека)
и `UiNavigator` (`src/D2.Data/Ui`, правила стека): экран отдаёт событие элемента через `Fired`, хозяин
спрашивает навигатор, куда оно ведёт, и подтягивает узлы к стеку. Отдельного менеджера сцен в `autoload/`
нет: пока игра — это стек экранов интерфейса, хватает одной сцены. Появится карта или бой как отдельная
сцена — тогда и решать, где живёт смена сцен.
