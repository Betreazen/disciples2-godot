# Инструменты авторов: редактор карт и моддинг

Комплект документов для сессий, которые будут делать инструменты. Написан 16.10.2026 по коду `main` 3eb56dc. Подчинён
[`docs/principles.md`](../principles.md) и правилам [`CLAUDE.md`](../../CLAUDE.md) (безопасность рабочих копий, проверки
числами, граф graphify).

## Вопрос и решение

Вопрос пользователя: «Редактор карт должен быть сразу и средой разработки модов, или для модов лучше другой инструмент?»

**Решение: одно приложение — «Мастерская» (`D2 Studio`) с двумя рабочими пространствами «Карта» и «Мод» на общем ядре
`src/D2.Authoring`, плюс командная строка `d2mod` на том же ядре. Делаем по очереди: сначала «Карта» (замена ScenEdit),
у «Мода» сначала только командная строка (проверка, сборка, запуск), окна для таблиц — потом.**

Ранее решено (оркестратор, подтверждено этим комплектом): редактор — **новый**, в порте на Godot, не перенос ScenEdit.
ScenEdit оригинала остаётся для карт, которые должны идти и в Disciples 2. `.sg` — только импорт (экспорт — отдельная
поздняя веха, см. [`data-contract.md`](data-contract.md) §6).

### Почему не два отдельных инструмента

| Довод | Что из него следует |
|---|---|
| Карта ссылается на содержимое мода: новый юнит, предмет, заклинание, ориентир мода должны быть в палитре редактора карт, а проверка карты — знать о них | редактор карт обязан читать слои модов → ему нужно ядро слоёв в любом случае |
| Карта **живёт в моде**: уже сейчас сценарии порта доставляются слоем (`mods/port-synth/data/scenarios/*.json` + `data/game/scenarios.json`, поиск `GameContent.ScenarioPath`) | «проект» редактора — это каталог мода; отдельный «проект карты» был бы вторым понятием того же |
| Проверка, сборка, запуск игры с картой и с модом — одна и та же операция (`MapScreen.tscn --scenario … --mods …`) | одно ядро проверки и запуска, иначе два расходящихся набора правил |
| Опыт индустрии (ниже): где содержимое и карты связаны (Warcraft III, Creation Kit), инструмент один; где мод — это просто файлы (Paradox, VCMI, OpenRA), редактор карт отдельно, а модинг — текст + утилиты | у нас связь сильная, но таблицы правил — текстовые JSON → гибрид: одно приложение, модинг сначала через CLI |
| Агенты и CI работают без окна: проект доказывает всё числами (`ui-render-check`, харнессы) | командная строка обязательна при любом варианте; окно — обёртка над теми же командами |

### Почему не «всё в одном окне сразу»

Окна редактирования 31 таблицы правил (`data/rules/*.json`) — большой объём работы с малой отдачей, пока у таблиц нет
схемы и слоя модов (их сейчас нет: `GameBook.Load(rulesDir)` читает один каталог, см.
[`modding-kit/spec.md`](modding-kit/spec.md) §2). Сначала ядро + CLI дают модам правила, проверку и упаковку; окна таблиц
строятся поверх, когда схема устоится.

### Как у других

| Пример | Устройство | Что берём |
|---|---|---|
| Warcraft III World Editor | одно приложение: Terrain, Object Editor (таблицы юнитов/способностей как наложение на базу по id), Trigger Editor, Import Manager; карта несёт свои правки объектов | правки таблиц — **наложение по id** с видом «база / изменено»; триггеры — список условий и эффектов с подстановкой ссылок |
| Bethesda Creation Kit | одно приложение на всё; плагин `.esp` — слой поверх `.esm`, конфликты слоёв видны | проект = слой; окно конфликтов «кто перекрыл запись»; правка базы невозможна — только переопределение в своём слое |
| Paradox (EU/CK/HoI) | официального редактора нет; моды — текстовые файлы, лаунчер, проверка ошибок в журнале игры, отладочные команды в игре | данные — текст, читаемый человеком и diff-ом; журнал ошибок загрузки с файлом и строкой |
| Heroes 3 HotA / VCMI | отдельный редактор карт; VCMI: моды — JSON + `mod.json` с зависимостями и версиями, лаунчер модов | `mod.json` с `version`, `dependencies`, `conflicts`; редактор карт открывает карту в контексте набора модов |
| OpenRA | редактор карт встроен в игру (тот же движок и рендер), правила — YAML-наложения, утилита `OpenRA.Utility` для проверки и обновления правил | редактор на **том же рендере**, что игра (`MapView`); CLI-утилита проверки и миграций |
| Godot-редакторы (Pixelorama, игры на Godot с встроенными редакторами уровней) | приложение на Godot, `Control`-интерфейс, `UndoRedo`, сцены редактора отдельно от сцен игры | интерфейс редактора — стандартные `Control` Godot, а не экраны игры; одна кодовая база с игрой |

Итог: связь «карта ↔ содержимое мода» сильная (как у WC3/CK) → одно приложение и общее ядро; правила — текст (как у
Paradox/VCMI/OpenRA) → CLI первой и окна таблиц позже.

Порядок работ (сводно): **K0 (слой правил и схема таблиц) → E0–E2 (редактор: открыть, рельеф, объекты, сохранить) →
K1–K2 (`d2mod validate/pack/run`) → E3–E5 (отряды, события, проверка, запуск) → K3+ и E6**. K0 стоит первым, потому что без
слоя правил мод не может добавить юнит, а карта — поставить его.

## Вопросы пользователю (сводно)

Подробности и рекомендации — в документах, здесь — список.

1. Имя приложения: «Мастерская» / «D2 Studio» / другое. Рекомендация: «Мастерская» в интерфейсе, `D2.Studio` в коде.
2. Экспорт карты в `.sg` для оригинала — нужен ли и когда ([`data-contract.md`](data-contract.md) §6). Рекомендация:
   не в первой версии; позже — «экспорт с проверкой совместимости» для карт без возможностей порта.
3. Таблицы правил: оставить колонки как в `.dbf` (`UNIT_ID`, `NAME_TXT`) со схемой-описанием или перевести в формат
   с именами по смыслу ([`modding-kit/spec.md`](modding-kit/spec.md) §3). Рекомендация: сначала схема поверх как есть, миграция — отдельно.
4. Мод и правки таблиц: наложение строк по ключу (рекомендация) или замена таблицы целиком.
5. Встроенный в игру редактор (как OpenRA) или отдельный запуск «Мастерской». Рекомендация: отдельная главная сцена
   того же проекта Godot, запуск игры с карты — отдельным процессом.
6. Генератор случайных карт (в ScenEdit есть слабый `DLG_RANDMAP`, у сообщества — D2RSG/`rsg.exe` с шаблонами на Lua) —
   делать ли и когда. Рекомендация: после E5, командой ядра в формат порта, шаблоны — данными (опора — алгоритм D2RSG,
   `../disciples-modding/reference/D2RSG/docs`).
7. Размер карты больше 144 для карт только порта. Рекомендация: разрешить, с запретом экспорта в `.sg`.
8. Язык оригинала карты: язык автора (рекомендация) или всегда английский.
9. Приставки id новых строк таблиц модов: реестр в `docs/modding.md` или хэш `id` мода. Рекомендация: реестр.
10. Загрузка сохранения с другим набором модов: запрещать или предупреждать. Рекомендация: предупреждать.
11. Скриптовые расширения модов (Lua, сборки .NET): рекомендация — нет до отдельного решения, механика — в `D2.Rules`.
12. Горячая перезагрузка в идущей партии: рекомендация — только экраны, строки, графика, звук; правила и карта — перезапуском.
