# План оптимизации ресурсов и прогрессивной загрузки

Статус: план будущего конвейера. Исходные assets и импортёры Godot остаются эталоном.
Все производные web-файлы создаются в отдельном output будущего проекта.

## 1. Подтверждённая исходная точка

Снимок 22.09.2026, байты файлов, без стоимости файловой системы и распаковки в память:

| Набор | Файлов | Байтов |
|---|---:|---:|
| assets/gfx | 148 209 | 2 367 989 450 |
| assets/ui | 2 341 | 109 361 294 |
| assets/video | 110 | 211 023 067 |
| Все assets | 150 660 | 2 688 373 811 |
| data | 70 | 7 239 122 |

Для gfx проверены **все** ссылки images и frames из `data/gfx/*.json`:
2 446 images, 10 383 animations, 134 210 ссылок кадров; 136 656 уникальных файлов,
1 756 912 297 байт, отсутствующих файлов 0.
Разница с полным каталогом — **611 077 153 байта (25,8% gfx)**: промежуточные материалы,
JSON распаковщика и/или файлы вне этих runtime-описей. Это кандидаты на исключение из
web-поставки после проверки иных потребителей, не разрешение удалить их из исходников.

`BatUnits`: 4 909 из 4 912 анимаций имеют заявленный холст 800×600; две 326×326,
одна 800×700. `BattleScene` задаёт anchor (400,490). Один RGBA8-кадр 800×600 занимает
1 920 000 байт ≈ 1,83 МиБ без mipmaps. Много прозрачных пикселей может почти ничего
не стоить в PNG на диске, но дорого стоит в текстуре. Реальный процент прозрачности
и потенциальная экономия trim ещё **не измерены**.

Не смешивать четыре метрики: байты в сети, байты постоянного кэша, CPU-память после
decode и GPU-память. Переход PNG → WebP обычно меняет первые две, но не RGBA8-текстуру.

## 2. Порядок конвейера

```text
read-only masters + импортные описания + правила
  → проверка ссылок и нормализация ID
  → граф зависимостей сценариев/действий
  → канонические пиксели / media masters
  → trim + pixel dedup + metadata
  → atlas pages / codec variants
  → разделение bootstrap / public / SP / private MP
  → manifest с полными хешами + отчёт качества/размера
  → staging browser tests
  → публикация immutable release
```

Входной fingerprint включает исходный хеш, настройки, версии кодировщика и atlas builder.
Повторная сборка с теми же входами должна воспроизводить байты; если codec не обеспечивает
детерминизм при выбранной многопоточности, закрепить воспроизводимый режим и отдельно
хешировать decoded reference. Сборка не должна читать неявные файлы из соседней игры
в production. Старые `.ff/.dbf/.sg/.bik` остаются только в offline-импорте.

## 3. Граф зависимостей

Паковать по **совместной востребованности**, а не только по исходному архиву или расе.
Уровни: bootstrap; common terrain/UI; семейство юнита и map/battle-действия; эффекты;
сценарные данные; язык/озвучка; необязательные media.

Reachability строить от экранов, начальных отрядов, построек и сценарных событий.
Учесть будущий найм, upgrade-цепочки, превращения, призыв, генерацию наград,
нейтралов, союзников и модификаторы. Список только стартовых юнитов **недостаточен**.
Граф доказывает доступность всех допустимых зависимостей, но не требует скачивать их сразу.
Динамическое неизвестное имя должно приводить к ошибке сборки либо зарегистрированной
fallback-группе; тихое отсутствие финального эффекта недопустимо.

Большой каталог не склеивать в race-all на сотни мегабайт. Расовый manifest ссылается
на мелкие группы. Общая текстура может иметь несколько логических владельцев без копии.
Глобальная дедупликация не должна вынуждать загружать гигантский атлас ради одного кадра:
малое повторение байтов иногда выгоднее общей тяжёлой зависимости.

## 4. Изображения и анимации

### 4.1. Канонизация и прозрачность

Базовое представление — RGBA8, исходный размер/anchor, стабильный цветовой профиль,
явные alpha/blend semantics. World gfx уже проходит magenta-key в импортёре; UI ещё
может вырезать его при загрузке. Перенести это в web-build, сохраняя исходный результат.
Не заменять любой розовый пиксель без проверки правил конкретного источника.

Trim искать по ненулевой альфе, сохраняя полупрозрачные тени и эффекты. Не вводить порог
«почти прозрачное → ноль» в lossless-профиле. Пустому кадру оставить длительность и
события; его можно представить ссылкой на один прозрачный texel.

Для каждого кадра хранить original_size, original_anchor, trim_offset, trimmed_size,
atlas_page, atlas_rect, duration и event markers. После обрезки:

`draw_top_left = world_anchor - original_anchor + trim_offset`.

Проверить атакующего/защитника и слои отдельно. В текущем `BattleScene` у сторон свои
кадры; автоматическое зеркалирование «ради экономии» может изменить вид и запрещено
без доказательства пиксельной эквивалентности.

### 4.2. Дедупликация

Ключ: полный SHA-256 канонических пикселей + размеры + формат. Для кандидата на
совпадение дополнительно сравнить байты, а anchor/duration/events хранить на ссылке кадра.
Текущие хеши анимаций не являются полными хешами отдельных файлов и не заменяют этот этап.

Последовательные одинаковые кадры можно объединить длительностью, если сохранены
моменты событий. Безусловно удалять «дубли» из timeline нельзя: изменится темп удара.
Delta-compression кадров — отложенный эксперимент: он усложняет произвольный доступ
и GPU-upload и не является обязательной оптимизацией.

### 4.3. Атласы

Исходный предел страницы — 2048×2048, меньшие страницы при плохом заполнении;
4096×4096 только после проверки MAX_TEXTURE_SIZE, upload time и памяти.
RGBA8-страница 2048² — 16 МиБ, 4096² — 64 МиБ, независимо от веса PNG/WebP.
Не заполнять минимальный пакет десятками полупустых страниц.

Группы: один/несколько совместно используемых юнитов, UI-состояния соседних экранов,
общие эффекты. Удар, idle, death можно разнести, если это не увеличивает число смен
текстур в обычном бою. Поворот кадров внутри атласа сначала отключён — проще сверка.
Padding/extrusion задаётся под фильтрацию; тестировать края на разных фонах, nearest
и масштабировании. Mipmaps для UI/спрайтов исходно не создавать; для масштабируемой
земли принимать отдельно с учётом ≈1/3 добавочной GPU-памяти.

Измерить одновременно atlas occupancy, decoded bytes, смены текстур/draw calls,
время upload и extra bytes предзагрузки. «Меньше файлов» само по себе не критерий успеха.

### 4.4. Кодеки

Первый воспроизводимый вариант — оптимизированный PNG/PNG-atlas. Второй — lossless WebP.
Не предполагать поддержку WebP текущим Rust-декодером: проверить crate features либо
декодирование браузером и конкретный путь передачи пикселей/текстуры в renderer.
Оставить PNG fallback. [Параметры cwebp](https://developers.google.com/speed/webp/docs/cwebp).

Lossy WebP/AVIF — только для подходящих фонов после сравнения; не исходный формат
текста, иконок и контуров. KTX2/Basis и GPU compression — отдельный следующий этап:
проверить transcoder, форматы устройства и путь загрузки через выбранный framework.
Их нельзя считать автоматически доступными в Macroquad. Runtime-uncompressed fallback обязателен.

## 5. Земля, туман и объекты

Не скачивать огромный предрендер всей карты как обязательный ресурс. Исходно использовать
компактные клетки + общие тайлы/маски + кэш чанков, как уже делает концептуально Godot.
Сравнить два прототипа: постепенная CPU-сборка в worker и отрисовка чанка в render target.
Ключ кэша включает версию terrain assets, seed/variant и revision изменённых клеток.
Ландшафт меняется по ходу игры — без invalidation старый чанк станет ошибочным.

Туман отделяется от земли. Чанк пересобирается при изменении самой местности, а не
каждом раскрытии клетки. Для MP не включать в кэш недоступную игроку terrain-информацию.
Следующий экран камеры можно предзагружать, используя только разрешённые данные.
Ограничивать одновременно CPU-чанки, GPU-чанки и очередь ещё не загруженных результатов.

## 6. Видео: FFmpeg применим, но из правильного источника

Текущий конвейер конвертирует Bink в Theora/Vorbis для Godot. Большинство роликов в
описи имеет около 15 FPS; встречаются 640×360, 800×600, 197×347 и 32×32.
Не апскейлить их до 720p автоматически и не повышать FPS ради браузера.
Новые версии кодировать из исходного Bink/master, не из уже lossy Theora.

Базовые варианты для проверки: MP4/H.264 + AAC и WebM/VP9 + Opus; AV1 отложить до
измерения выигрыша и декодирования на целевых устройствах. Выбор делать по возможностям
браузера и пробному воспроизведению; контейнер/расширение само по себе не гарантирует codec.
[Форматы web-video](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs),
[проверка canPlayType](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/canPlayType).

Длинные непрозрачные ролики — HTMLVideoElement через JS bridge, потоково по отдельному URL,
вне монолитного игрового пакета. Начальный путь — DOM overlay, синхронизированный с
размером канвы; не декодировать видео в Rust только ради заявления «всё на Rust».
Короткие портреты/переходы отдельно сравнить как видео, атлас или статический fallback.
Прозрачные анимации юнитов остаются атласами, а не универсальной видеозаменой.

MP4 с faststart, поддержка HTTP Range на storage/CDN; не накрывать видео общим сжатием
пакета. Для исходников 360p начать с родного разрешения; дополнительный меньший вариант
только при достаточной читаемости. Aspect ratio сохраняется, odd dimensions обрабатываются
padding при необходимости. Стартовые параметры эксперимента, не утверждённые настройки:
H.264 CRF 20/24/28; VP9 CRF 28/32/36 с ограничением пикового битрейта после измерения.
Точные FFmpeg invocation и версии зафиксировать в будущем asset-build recipe.
[FFmpeg CLI](https://ffmpeg.org/ffmpeg.html).

Проверки: длительность, кадры/таймстемпы, AV-sync, первый/последний кадр, seek,
цвета, блокинг, looping. PSNR/SSIM помогают найти ухудшение, но не заменяют просмотр
контуров, текста и движущихся сцен. Не обрезать паузы и не удалять звук без решения дизайна.

## 7. Аудио

Текущие восемь `.ogg` — озвучка брифингов, а не доказательство, что вся музыка/эффекты
оригинала уже импортированы. После Godot G0 провести полную аудиоинвентаризацию:
источник, язык, каналы, длительность, loop points, пики и роль.

| Тип | Кандидат | Стратегия |
|---|---|---|
| Музыка | Opus, альтернативный AAC/MP3 по браузерной проверке | Потоковое media; не decode всей коллекции в PCM |
| Голос | Opus, отдельные языковые packs | Mono только если исходная семантика позволяет |
| Короткие эффекты | PCM для очень коротких / поддержанный сжатый формат | Ограниченный Web Audio buffer cache |
| UI click | Малый базовый набор | Готов до первого клика |

Стартовые bitrate-кандидаты: голос 32/48/64 кбит/с; музыка stereo 96/128/160 кбит/с.
Это сетка эксперимента, не гарантия качества. Сохранять исходную частоту либо осмысленно
ресемплировать, не переносить stereo → mono и не нормализовать каждый эффект независимо:
это может уничтожить авторские соотношения громкости. Проверить паузы, loop и codec delay.

Декодированный stereo float32 48 кГц за минуту ≈23 МБ; маленький сжатый файл не означает
малый AudioBuffer. Ограничить число голосов, освобождать буферы, при нехватке приоритизировать
важные звуки. Браузерный audio adapter тестируется отдельно от встроенного звука framework.
Autoplay failure оставляет меню рабочим; активация по клику.
[Ограничения autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay).

## 8. Шрифты, текст, данные

Сначала один набор начертаний для UI, glyph cache с лимитом; кириллица, латиница,
цифры и используемые символы обязательны. Subset не должен ломать произвольные имена:
fallback либо явный допустимый набор. WOFF2 удобен DOM, но не автоматически читается
font renderer Macroquad; для canvas-части проверить TTF/OTF путь и цену glyph-atlas.

JSON правил/UI оставить читаемым source и использовать HTTP Brotli. Бинарное представление
добавлять лишь при измеренной задержке parse/размере. Комментарии, trace и импортные
таблицы, не нужные клиенту, не включаются. Локализация грузится выбранным языком.

## 9. Формат поставки v1

Не писать собственный контейнер до доказанной потребности. Release manifest описывает
логические bundles, состоящие из immutable atlas/metadata/audio objects. Группа загрузки
не обязана быть одним физическим файлом. Для множества мелких metadata допускается
стандартный ZIP с лимитами; уже сжатые media хранить без повторного Deflate.
Длинное видео/музыка остаются отдельными URL для streaming/Range.

Пример полей content object (значения условные):

```json
{
  "schema": 1,
  "asset_id": "unit/fighter/battle-idle",
  "variant": "original-lossless",
  "url": "/content/<full-sha256>.png",
  "sha256": "<full-sha256>",
  "transfer_bytes": 180000,
  "decoded_bytes": 4194304,
  "width": 1024,
  "height": 1024,
  "dependencies": ["unit/fighter/battle-idle-metadata"]
}
```

Хеш относится к каноническому телу объекта после снятия HTTP Content-Encoding, а не
случайно к Brotli-представлению; семантика фиксируется в schema. `transfer_bytes` зависит
от варианта и HTTP encoding и служит оценкой, не границей доверия. Настоящие лимиты
размера/размерностей применяются перед allocation. Примеры `<full-sha256>` не валидные release values.

## 10. Scheduler и кэши

Состояния ресурса: Missing → Fetching → Verified → Cached/Encoded → Decoding → Uploading
→ Ready; отдельно Failed/Cancelled/Evicted. Есть одна shared in-flight операция на hash.
При смене сценария результаты со старым generation ID не прикрепляются к новой сцене.

Приоритеты: P0 текущий экран, P1 следующий подтверждённый переход, P2 вероятная игра,
P3 необязательное. Для начала 2–4 сетевых запроса и 1 тяжёлая decode/upload-цепочка;
настраивать по измерениям. Асинхронный fetch не означает отсутствие freeze от decode.
Upload дробить по страницам; стартовый бюджет главного потока — 2 мс/кадр на обработку
готовности (цель, конкретная GPU-операция может превышать его и потребовать меньшего atlas).

Четыре независимых кэша: HTTP/CDN; browser encoded Cache Storage; CPU decoded;
GPU textures/audio buffers. Saves и metadata в IndexedDB. Не дублировать все packs
одновременно и в Cache Storage, и IndexedDB. Wasm linear memory после освобождения
allocations может не уменьшить свой high-water mark: предупреждать пики, не полагаться
на мгновенное возвращение памяти ОС.

Браузер может отказать в записи или удалить данные origin; quota оценочная, persistence
не гарантируется. При отказе игра продолжает работать с ограниченным memory cache,
SP предлагает экспорт сейва. Вытеснять неподписанные сценой encoded assets по LRU;
свои saves защищать от очистки приложения, но не обещать защиту от очистки браузером.
[Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## 11. Измеримый эксперимент оптимизации

Выбрать UI с текстом/кнопками, десяток разных боевых юнитов обеих сторон, длинный эффект,
тени, воду/берег, map movement, короткий ролик меню, длинный брифинг и голос.
Записать исходные encoded/decoded bytes, число файлов, cold load/decode/upload times.
Сравнивать по шагам, чтобы видеть вклад каждого:

1. Только исключение нереференсных материалов.
2. Trim с восстановлением оригинального холста.
3. Pixel dedup с сохранённой timeline.
4. Атласы разных размеров и группировки.
5. PNG против lossless WebP; отдельно допустимый lossy-профиль.
6. Кандидаты видео/аудио и их streaming.
7. Полный путь меню → карта → первый бой с холодным и тёплым кэшем.

На lossless-профиле восстановленные видимые RGBA должны совпасть с эталоном; допускается
канонизация RGB полностью прозрачных пикселей. Любые иные отклонения — дефект или
отдельно одобренная художественная смена, не побочный эффект оптимизации.
Итоговый процент сжатия и размер первого сценария определить экспериментом, не обещать заранее.
