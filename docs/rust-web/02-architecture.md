# Архитектура Rust-клиента и общего ядра

Статус: проект. Реализация начинается после ворот G0 из [плана](06-implementation-plan.md).

## 1. Технологическое решение

Исходный выбор — **Macroquad поверх Miniquad**, Rust/Wasm для браузера. Это библиотека
для игрового цикла, ввода и 2D-рисования, а не замена всех редакторских инструментов Godot.
Macroquad документирует HTML5 и автоматический geometry batching, но это не гарантирует
достаточное число draw calls для конкретного порядка спрайтов нашей игры.
[Официальная документация](https://docs.rs/macroquad/latest/macroquad/).

Почему этот кандидат: основная сцена — 2D-спрайты, карты, маски и интерфейс из данных;
нет обязательной потребности в физике, 3D и универсальном ECS. Сначала использовать
готовый batch renderer. Собственный renderer не является исходной обязательной задачей.

Ворота принятия: реальный бой со слоями и тенями, карта с туманом, текст на русском,
ввод имени через IME, воспроизведение видео, асинхронная загрузка, восстановление WebGL
контекста и измерение памяти в трёх семействах браузеров. Проверить точную версию crate,
JS bundle и доступные target features; закрепить Cargo.lock и toolchain вместе.

Если Macroquad ограничивает измеренный сценарий, сначала локализовать ограничение:
платформенный адаптер, miniquad rendering API или отдельный pass. Переход к Bevy/wgpu —
новое архитектурное решение после отчёта, не автоматическое «ускорение через другой движок».

## 2. Компоненты и границы

```text
Браузер
  HTML/JS shell ── Fetch / Cache / IndexedDB / media / WebSocket
        │
  Rust client.wasm: UI → команды → Session
        │                          ├─ LocalSession → sim worker → core
        │                          └─ RemoteSession → WebSocket → сервер
        └─ ViewState → renderer → Macroquad → WebGL

Сервер
  Axum/Tokio → последовательная очередь комнаты → core → PostgreSQL
                       └─ проекция для игрока → WebSocket

Содержимое
  импорт → проверенные промежуточные данные → asset build → immutable CDN
                                           └─ private scenario → сервер
```

Одна библиотека правил применяется локально и на сервере. UI обращается к Session,
получает доступную игроку модель представления и события; он не меняет World напрямую.
RemoteSession не рассчитывает авторитетный результат и не получает скрытый World.

## 3. Предлагаемое дерево будущего репозитория

```text
crates/
  core/             state, rules, rng, ai, commands, events, projection
  protocol/         сетевые DTO, версии, форматы save/content
  client/           меню, карта, бой, scheduler загрузки, renderer
  sim-worker/       wasm-обёртка core для одиночной симуляции
  server/           API/WS, комнаты, persistence, compute pool
  asset-build/      зависимости, trim/dedup/atlas, manifests, отчёты
  parity/           обмен fixtures с эталоном, replay и проверки
web/
  shell/            HTML/CSS, JS bridge и Worker bootstrap
content-src/        описания, настройки сборки, ссылки на master-ресурсы
tests/              интеграционные, browser и нагрузочные сценарии
docs/               решения, форматы, результаты измерений
```

Это логические границы. Не создавать по crate на каждую формулу, экран или тип ресурса.
Рендер и загрузка сначала модули client; правила, AI и модель сначала модули core.
Минимум зависимостей у core, без Macroquad, Tokio, ОС, JS и сетевых клиентов.
protocol использует отдельные внешние DTO, не сериализует внутренний World как сетевой ответ.
core не зависит от protocol: преобразование на границе.

## 4. Игровая модель

Статические определения юнитов, атак и предметов загружаются один раз на ruleset.
В состоянии экземпляра находятся ID, изменяемые значения и цепочки модификаторов,
а не копии всех справочников. На сервере определения разделяются между комнатами.

Устойчивые строковые ID остаются в контенте и внешних форматах. Во внутреннем ядре
допустимы типизированные числовые ID и массивы после построения проверенной таблицы
соответствий. Индексы памяти/указатели не сохраняются и не передаются по сети.
Предпочитать простое владение состоянием одним обработчиком, а не общий граф Arc/Mutex.

Переход модели: `команда + World + Ruleset + RNG → новый World + DomainEvents`.
Команда валидируется до расхода RNG и изменения мира. Время из ОС не читается в правилах;
таймер приходит явно как системная команда. Ошибка не должна оставлять половину покупки,
движения или атаки. Для начала допустима обработка на рабочей копии состояния;
стоимость копирования измеряется до усложнения транзакций в памяти.

Не переносить автоматически harness-only код в release. Например, `EngineRng.Fit`
подбирает последовательности по корпусу; это инструмент проверки, а не обычная работа
ИИ. Он не нужен браузеру или production-серверу.

## 5. Детерминизм и переносимость

- Размеры целых чисел явные; политика overflow повторяет эталон (checked/wrapping
  в нужных местах), не зависит от debug/release.
- Не полагаться на порядок HashMap; сортировать при выборе целей, разрешении равенств,
  сериализации и хешировании состояния.
- Сохранить целочисленное деление, знаки, case-insensitive ID и порядок RNG-вызовов.
- Ввести раздельный RNG представления и правил; случайная начальная фаза спрайта
  не расходует генератор боя.
- Полное состояние игрового RNG входит в save. Для текущего R250 это таблица 250
  16-битных слов и индекс; одного seed/index недостаточно для произвольного продолжения.
- Подтвердить равенство результатов native Rust, wasm Rust и C#-эталона на одинаковых inputs.

Режим совместимости получает стабильный `ruleset_id`. Будущий баланс и механики меняют
ruleset, не golden-ожидания эталона. Для сети RNG-состояние и секретный seed клиенту
не отправляются. Совместимость с оригинальным RNG не даёт криптографической защиты
от предсказания; соревновательный продукт может потребовать нового серверного RNG
в отдельном ruleset.

## 6. Браузерная граница

«Полный Rust» допускает JS shell для Web API. JS не дублирует правила; он возвращает
асинхронные результаты через ID запросов и очередь сообщений. Не считать, что файл
в Cache Storage автоматически доступен через std::fs или Macroquad load_file.
Способ передачи bytes/decoded images/textures в выбранный loader проверяется в прототипе.

Исходная интеграция — официальный JS loader/bundle Macroquad + небольшой plugin bridge.
Не смешивать его автоматически с wasm-bindgen loader. Если выбран wasm-bindgen для
worker/API, это отдельная совместимая сборка с проверенным ABI, без двух конкурирующих
инициализаций одного main module. [Механизм JS interop](https://macroquad.rs/articles/wasm/).

Main thread владеет WebGL и UI. Одиночное ядро работает в отдельном Web Worker:
команды и изменения состояния передаются сообщениями, не весь World каждый кадр.
Это отдельный экземпляр Wasm с отдельной памятью. CPU-декодирование также можно вынести
в ограниченный worker, но GPU-upload остаётся на потоке владельца контекста.
Обычный worker с передачей буферов не требует SharedArrayBuffer; shared-memory
multithreading и COOP/COEP не являются исходным требованием.
[Документация Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers).

План Б при проблемах worker-интеграции: расчёт маленькими порциями с yield в event loop.
Один `async` сам по себе не делает CPU-цикл неблокирующим. Нельзя принимать этот план,
если максимальный сценарий замораживает UI. Серверный Tokio runtime в браузер не переносится.

## 7. Представление и рендер

Сначала воспроизвести UI из `data/ui`, используя сохранённые координаты, стили и ID.
Rust-клиент содержит только web-необходимые маршруты; runtime не наследует мёртвые
сетевые/desktop-экраны оригинала автоматически. Сходство картинок и работа ввода — разные тесты.

Renderer получает список видимых draw items: atlas/page, UV, transform, слой, blend,
clipping. Порядок прозрачных спрайтов сохраняется. Нельзя сортировать все элементы
по текстуре, если это меняет перекрытие юнитов, теней и объектов. Batching допустим
между совместимыми соседями либо внутри доказанно переставляемой группы.

Камера отсекает невидимые объекты; анимация скрытых спрайтов не создаёт GPU-работу.
Статическая земля кэшируется чанками. Туман — отдельный слой/маска; его изменение
не обязано пересобирать всю землю. Для MP статический кэш содержит только разрешённую
геометрию, если сама местность скрыта. Анимированная вода — отдельный слой.

Nearest и оригинальное разрешение — исходная настройка; DPI экрана не должен без
ограничений умножать render target. Ввести лимит backing resolution и внутренний
render scale. Сцена/атлас освобождаются по владельцу и бюджету, не только по числу файлов.
При потере GPU-контекста восстановить видимые текстуры из кэша, игровое состояние сохранить.
Практики WebGL, включая batching и управление ресурсами:
[MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

## 8. Цикл и планирование

`requestAnimationFrame` даёт возможности отрисовки, но не гарантирует 60 Гц и может
приостанавливаться в фоне. Ограничитель использует timestamps, учитывает высокочастотные
мониторы и не строится на busy-wait. После возврата не проигрывать тысячи накопленных
кадров. Клип вычисляет актуальный вид по времени; обязательные игровые события живут в модели.
[Поведение rAF](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

В активном кадре: обработка ввода/сетевых сообщений → ограниченный объём результатов
загрузки → визуальная интерполяция → построение draw list → рисование.
CPU-декодирование и массовая загрузка текстур не выполняются без лимита в этом цикле.
Режим покоя может пропускать рисование, если нет изменений; браузерные callbacks при
этом могут продолжаться. Критерий — измеренная экономия CPU, а не название режима.

## 9. Чего Rust не обеспечивает автоматически

PNG/WebP декодируется в пиксели и обычно занимает одинаковый объём RGBA после загрузки.
Wasm не ускоряет сеть и не уменьшает исходные картинки. Отсутствие GC в Rust не
гарантирует отсутствие пауз в web-вкладке. GPU-работа определяется рисованием, разрешением
и overdraw. Серверные расходы зависят от модели комнат, хранения и темпа команд.
Поэтому выбор стека и оптимизация assets имеют отдельные ворота измерений.
