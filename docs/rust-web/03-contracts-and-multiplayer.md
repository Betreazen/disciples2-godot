# Контракты, сеть и сохранения

Статус: проект форматов v1. Примеры — спецификация для будущей реализации, не готовые API.

## 1. Версии и идентичность

Каждая партия закрепляет `ruleset_id`, `ruleset_hash`, `scenario_id`, `scenario_hash`,
`content_release` и `save_schema`. Соединение согласует `protocol_version` и `client_build`.
Content release связывает проверенную совместимую комбинацию manifests и артефактов.
Хеши — полные SHA-256, а не текущие сокращённые 16 hex из импортных описей.

Публикация новых ресурсов не меняет активную партию. Старые releases хранятся, пока есть
поддерживаемые сейвы/комнаты, ссылающиеся на них. Миграция создаёт новую копию сохранения
и запись о преобразовании; не перезаписывает единственный оригинал.

## 2. Общие команды ядра

Начальный набор: StartScenario, Select/MoveStack (выбор визуальный — только клиент),
AttackStack, EndTurn, HireUnit, Build, ExchangeUnits, Trade, CastSpell, UseItem и
боевые Attack/Defend/Wait/Retreat/UseBattleItem. Точный состав выводится из завершённого
Godot-порта; список здесь не подменяет спецификацию игровых механик.

Локальный и сетевой Session принимают одни и те же намерения. Сервер сам вычисляет цену,
урон, допустимый путь и результаты RNG. Клиент не присылает «готовый новый World».
Маршрут клиента может быть пожеланием, но сервер проверяет все шаги и не сообщает
причины, раскрывающие ещё невидимого противника. Допустимое поведение упора в скрытый
объект закрепляется ruleset и повторяет эталон.

## 3. Транспорт v1

HTTPS для каталога/авторизации/создания комнаты, WSS для команд и состояния партии.
Начальный формат — ограниченный по размеру JSON с явными DTO; бинарный протокол
вводится только при подтверждённой цене сериализации или трафика.

Пример команды:

```json
{
  "protocol_version": 1,
  "room_id": "room-123",
  "command_id": "client-session-9:42",
  "expected_view_seq": "71",
  "turn_token": "opaque-server-issued-token",
  "type": "MoveStack",
  "payload": {"stack_id": "stack-17", "destination": [18, 24]}
}
```

Игрок определяется серверной сессией, не полем player_id запроса. Большие counters
передаются десятичными строками, чтобы JS не терял точность u64. Числа координат имеют
диапазоны; неизвестная обязательная версия/тип команды отклоняется.

`expected_view_seq` относится только к проекции этого игрока. Сервер хранит внутреннюю
revision отдельно: разрывы глобального счётчика не должны раскрывать скрытые действия.
`turn_token` связывает право команды с текущей фазой/ходом; неподходящий token требует
resync. `command_id` обеспечивает идемпотентность; повтор с другим payload — ошибка.

Ответ состоит из подтверждения/отказа и последовательности ViewDelta:

```json
{
  "type": "ViewDelta",
  "view_epoch": "session-view-6",
  "base_seq": "71",
  "seq": "72",
  "events": [
    {"type": "StackMoved", "stack_id": "stack-17", "to": [18, 24]}
  ]
}
```

Epoch меняется при полном resync; delta применяется только к точному base_seq.
Потеря промежуточного состояния приводит к запросу snapshot, а не к догадке клиента.
Команда может быть подтверждена без визуального изменения; receipt и поток view различаются.
Ошибки: WrongTurn, InvalidCommand, StaleView, UnsupportedVersion, RateLimited,
StorageUnavailable. Текст ошибки не содержит скрытых объектов, серверных путей и stack trace.

## 4. Порядок обработки и долговечность

На одну комнату — один последовательный обработчик. Для команды:

1. Проверить сессию, роль, лимиты и command_id; вернуть сохранённый receipt для повтора.
2. Проверить версии, turn_token и актуальность видимой проекции.
3. Рассчитать переход ядра на рабочем состоянии; при отказе не менять committed state/RNG.
4. В одной транзакции записать новую revision/snapshot, внутренние события и receipt.
5. После успешного commit заменить live state, построить разрешённые изменения и отправить.

Если БД недоступна, подтверждение успеха не отправляется. Если сервер упал после commit,
но до отправки, повтор command_id возвращает прежний результат. Уникальность
`(room_id, actor_id, command_id)` и проверка revision предотвращают двойное применение.

Первая реализация хранит current snapshot на каждой принятой команде и append-only
журнал команд/событий для диагностики. Это сознательно простой вариант; цену полного
snapshot измерить. При переходе к редким snapshots все промежуточные изменения должны
восстанавливаться из устойчивого журнала, включая RNG, а не зависеть от памяти процесса.

## 5. Жизненный цикл комнаты

`Lobby → Starting → Running → Paused/Completed → Archived`.

- Lobby: сервер проверяет доступные слоты, назначения рас и настройки.
- Starting: фиксируются версии; клиенты подтверждают свой стартовый набор; timeout
  возвращает комнату в Lobby, а не бесконечно удерживает ресурсы.
- Running: один активный стратегический ход, внутри него возможна очередь боевых решений.
- Paused: сохранены фаза, ход, боевое состояние и deadlines; применяется политика комнаты.
- Completed: окончательный результат и доступная игрокам история.
- Archived: состояние в БД, live simulation и GPU отсутствуют.

Отключение хозяина не удаляет партию: сервер владеет ею. Право менять настройки до старта
и право играть — отдельные разрешения. В двух вкладках одного игрока по умолчанию одна
активная управляющая сессия; вторая получает режим чтения или явно заменяет первую.

При бое между людьми ввод получает сторона активного бойца. Остальные участники комнаты
не могут выполнять экономические команды вне своей фазы. Автобой/защита по таймеру
являются явной системной командой согласно настройкам, не решением анимационного клиента.

## 6. Переподключение и медленные клиенты

Клиент передаёт room_id, view_epoch и последний подтверждённый view_seq после авторизации.
Если сервер сохранил допустимые deltas и epoch совпадает — отправляет недостающее.
Иначе строит свежий player snapshot и новый epoch. Полный World для resync не используется.

Snapshot содержит достаточно данных, чтобы восстановить текущую фазу/экран без повторного
ввода. Законченные анимации можно пропустить; неприменённые игровые эффекты — нельзя.
Отправленные, но неподтверждённые команды повторяются с прежними command_id.

Исходящая очередь ограничена. При накоплении устаревших deltas сервер переходит на resync
или закрывает соединение с возможностью восстановления. Медленный браузер не удерживает
бесконечный журнал и не блокирует другие комнаты. Heartbeats и timer jobs допустимы;
постоянного игрового tick на 30/60 Гц нет.

## 7. Туман войны и границы секрета

Разделить три набора:

| Данные | SP | MP |
|---|---|---|
| Графика, звук, общие определения | Публичные packs | Публичные packs |
| Полный сценарий/начальный World | Доступен локальной симуляции | Private на сервере, если содержит секреты |
| Текущее состояние мира | В локальном worker | Только сервер; игроку PlayerView |

PlayerView строится разрешительным списком. Отсутствуют скрытые позиции, HP, инвентарь,
очереди приказов ИИ, секретные события и RNG. Исчезнувший из видимости объект превращается
в явно ограниченное воспоминание, если это предусмотрено правилами; новые значения
для него не передаются. Проверить мини-карту, звуки, журнал боя, ошибки и reconnection,
а не только основную карту. Союзный обзор — часть ruleset.

Публичный manifest MP не должен кодировать размещение скрытых существ и сюжетные
условия. Предзагрузка по конкретному скрытому юниту тоже может раскрывать информацию;
вместо неё загружать публичные широкие группы или ждать раскрытия, допуская короткую паузу.
Не посылать клиенту полный снимок и «зашифровать» его ключом в том же клиенте.

**Ограничение защиты:** если тот же фиксированный сценарий доступен для скачивания в SP
или давно известен по оригиналу, его географию и начальные позиции нельзя сделать тайной
в MP. Фильтрация защищает текущее состояние партии. Для скрытой начальной генерации
нужны серверный seed и private-экземпляр сценария; это отдельный режим продукта.
Не обещать, что один только WebSocket-projection предотвращает все способы предсказания.

## 8. Сохранение v1

Envelope: magic/format, save_schema, ruleset_id/hash, scenario_id/hash, content_release,
mode, game_id, logical_revision, created_at, payload_hash, payload.
Timestamp служит метаданными и не влияет на детерминизм. Hash обнаруживает повреждение,
но не делает пользовательский SP-save доверенным сетевым состоянием.

Payload включает игроков/слоты, день/очередь/фазу, карту и изменённые клетки, отряды,
юниты и modifiers, инвентарь, экономику, дипломатию, сценарные флаги, состояние видимости,
активный бой с очередью действий и полный RNG. Pending UI-анимация восстанавливается
из модели или пропускается, не определяет исход партии.

Реальная полнота полей выводится из round-trip завершённого Godot-порта. Файл
`src/D2.Rules/Map/SaveState.cs` содержит некоторые модели чтения оригинала; его имя
не означает, что уже существует полноценный формат сохранения порта.

Начальный portable save — версионированный JSON, при необходимости сжатый стандартным
контейнером. Лимиты распакованного размера/ссылок/размеров карты проверяются до применения.
В IndexedDB сохранение и индекс записываются транзакционно; держать предыдущую успешную
версию. Автосейвы не зависят только от beforeunload: закрытие вкладки может не дать времени.

MP-save принадлежит серверу и включает приватные данные. Скачать игроку можно только
разрешённый экспорт; SP импорт не принимается в действующую сетевую комнату.

## 9. Контент и расширения

Моды первой версии — проверяемые данные и assets, без нативного/произвольного JS-кода.
Порядок наложения стабилен, разрешённые ID и зависимости проверены; разрешённый набор
фиксируется в release/ruleset. В MP правила публикует сервер, локальный override их не меняет.
Новые механики добавляются в core с версией и тестами, а не универсальным runtime-плагином
заранее. Редактор и пользовательская публикация — отдельные будущие инструменты.
