# План реализации после Godot-порта

Статус: будущая работа. Ни один пункт ниже не считается реализованным этим комплектом.
Последовательность отделяет проверяемый перенос от самостоятельного развития продукта.

## G0. Входные ворота: завершённый Godot

**Начинать Rust-реализацию только после G0.** Проверить:

- Из главного меню проходит полный сценарий до победы/поражения, включая бой и возврат,
  экономику, ИИ, города/отряды, события, сохранение/загрузку.
- Внешний вид и поведение приняты как рабочий порт оригинала. Открытые расхождения
  имеют список и решение; существующие «~99%» не являются доказательством полноты.
- Выпущен воспроизводимый desktop build с зафиксированным commit и toolchain.
- Зафиксированы фактическое число тестов и их результаты на этом commit; 1118 из
  нынешнего HANDOFF — историческое число, не будущий автоматический критерий.
- Сделаны независимые резервные копии корпусов/masters, описана процедура восстановления.
- Стабилизированы save schema и набор reference scenarios для переноса.

Выход: release reference, список известных расхождений, fixtures, screenshots/timelines,
реестр источников ресурсов. Текущие документы Godot не изменяются ради Rust заранее.

## P1. Проверка выбранного framework и browser bridge

Зависимость: G0. Создать отдельный репозиторий с Cargo.lock, pinned toolchain, release
Wasm build и статическим test host. Первый прототип должен содержать настоящие ресурсы:

1. Меню с русским текстом, кнопкой, списком и вводом имени.
2. Прокручиваемый участок карты с корректным порядком спрайтов и туманом.
3. Бой с несколькими слоями юнитов/тенями и исходным темпом кадров.
4. Fetch с отменой, encoded cache, две страницы атласа, eviction и повторная загрузка.
5. Video/audio через browser adapter, реакция на запрет autoplay.
6. Малое ядро в worker с командами; UI продолжает отвечать во время CPU-задачи.
7. Потеря WebGL context, high-DPI и 30/60 FPS cap.

Выход: запускаемый URL, воспроизводимая сборка, browser matrix и профиль загрузки/памяти.
Ворота G1: Macroquad принят по измерениям либо отклонён с конкретной причиной.
Если integration gate не пройден, не переносить всё ядро наугад; выбрать и проверить
альтернативный renderer/bridge. Минимальные performance budgets — в документе 07.

## P2. Конвейер контента v1

Зависимость: P1 определяет пути decode/upload. Сначала репрезентативный набор, затем весь
каталог. Реализовать source inventory, reachability, полные хеши, trim/offset, dedup,
атласы, PNG baseline и WebP experiment. Media — отдельные FFmpeg recipes с отчётом качества.

Сборщик выпускает public manifest, SP scenario blob, private MP scenario blob, atlas metadata,
release index, размер/decoded-budget report и список неразрешённых ссылок.
Все master-файлы читаются; output изолирован. Новое имя ID не должно молча ломать моды.

Выход: маленький bootstrap и сценарий с зависимостями; точные bytes до/после, browser load trace,
pixel reconstruction check, video/audio parity и проверка public/private.
Ворота G2: все обязательные ссылки разрешены, качество lossless-профиля совпадает,
спорные lossy-изменения не приняты автоматически, обновление затрагивает только нужные objects.

## P3. Ядро и проверяемый перенос правил

Зависимость: G0; полная миграция после G1. Порядок:

1. Модель ID/чисел, определения и строгая загрузка данных.
2. RNG и арифметика с native/Wasm/C# differential tests.
3. Правила и сессия боя, атаки, статусы, опыт, предметы и battle AI.
4. Карта, движение/pathfinding, туман, экономика, города, магия и сценарные события.
5. Стратегический/тактический ИИ и дипломатия.
6. Полная симуляция партии и save/load посреди карты/боя.

Портировать вертикальными наборами механик: типы → поведение → fixtures → тесты.
Не транслитерировать все C#-классы в Rust с Rc<RefCell> по умолчанию. Сохранять смысл
модели, использовать явное владение и ID; новые структуры принимаются через parity.

Harness-only подбор RNG и разбор журналов остаются в tools/parity, не в client release.
Неразобранное в эталоне поведение заносится в реестр, не маскируется улучшенным Rust AI.

Выход: headless core, нормализованные fixtures и diff report по каждой группе.
Ворота G3: нет необъяснённых расхождений на утверждённом корпусе, одинаковые snapshots
и outcomes native/Wasm, сохранение продолжает ту же RNG-последовательность.

## P4. Полная одиночная вертикаль

Зависимости: G2, G3. Связать UI → LocalSession → sim worker → PlayerView → renderer.
Реализовать каталог, выбор сценария/расы/лорда, загрузку по приоритетам, брифинг,
карту, города/отряды, бой, конец хода, итог сценария, настройки, autosave/continue/export.

Подключить весь web-необходимый UI эталона. Требуется список screen/state/command/error
и coverage, а не только красивые главное меню и экран боя. Map/battle rendering отделено
от состояния правил; renderer не принимает решений ИИ и не инициирует урон по кадру.

Выход: сценарий проходится целиком с cold cache и затем повторно с warm cache.
Ворота G4: корректность правил, отсутствие missing assets, прогресс загрузки, отмена,
возврат, ошибка сети/кэша, сохранение и восстановление в трёх браузерных семействах.

## P5. Авторитетный Rust-сервер

Зависимости: G3 и зафиксированные [контракты](03-contracts-and-multiplayer.md).
Реализовать Axum/Tokio service, session auth, rooms/slots, PostgreSQL schema/migrations,
последовательную обработку, bounded compute pool, receipt и atomic commit.

Начать с двух тестовых клиентов: одна команда проходит один раз, неверный ход отвергается,
проекция скрывает секреты, повтор после crash возвращает прежний результат.
Затем подключить RemoteSession существующего клиента; UI не становится вторым набором экранов.

Выход: создаваемая/продолжаемая комната, reconnect/resync, full snapshot не попадает в browser.
Ворота G5: duplicate/reorder/reconnect/crash tests, transaction-before-ack, hidden-state
noninterference tests и отсутствие неограниченных очередей.

## P6. Партия до пяти игроков

Зависимости: G4, G5. Lobby, сценарные слоты/раса, приглашения, readiness и версии,
последовательные ходы, бой двух людей, AI-слоты, пауза/таймеры, завершение.
Проверить 2–5 человек, разные сочетания ИИ, хозяин offline, две вкладки одного игрока,
медленный клиент и восстановление партии после рестарта сервера.

Выход: воспроизводимый многоклиентский сценарий и полный playtest партии до конца.
Ворота G6: все участники получают свои корректные views, один пользователь не может
менять чужие слоты/отряды, таймеры переживают рестарт, медленный клиент не блокирует сервис.

## P7. Оптимизация и эксплуатационная приёмка

Зависимости: G4 и G6. Зафиксировать реальные устройства/сеть; профилировать cold/warm
load, first battle, большие карты, end-turn AI, RAM/GPU, число upload/draw calls.
Оптимизировать по результатам: размер групп, соседние UI, codecs, batching, memory peak.

Сервер: нагрузочные profiles idle/active/AI burst/reconnect/save. Измерить capacity
до достижения latency/памяти, выбрать пределы admission и документировать конфигурацию.
Включить release pinning, backup restore, rollback, cache eviction и telemetry.

Выход: отчёт с цифрами и компромиссами, воспроизводимый deploy/runbook.
Ворота G7: бюджеты достигнуты либо пересмотрены явным решением на измерениях;
не скрывать провал изменением условий теста или отключением игровых систем.

## P8. Выпуск и дальнейшее развитие

После G7 — ограниченное тестирование, затем расширение аудитории по метрикам.
Совместимый ruleset остаётся reference. Новые механики/баланс имеют собственные tests,
ruleset version и описание влияния на сейвы. Новый UI/HD-профиль не должен требовать
переписывать чистые правила; это проверка границ архитектуры.

Будущие темы: touch, редактор, контентные моды, рейтинги, новый RNG для конкурентного
режима, новые расы/слоты, GPU compression, split-code загрузка, горизонтальный сервер.
Они не входят скрыто в оценку первого переноса.

| Сейчас | Будущая ответственность | Что переиспользуется |

| src/D2.Rules/Battle, Map, Units, Magic | core | Правила/порядок, не C# binaries |

| tests и corpus | parity | Тестовые случаи, журналы, golden inputs/outputs |

## Организация реализации

Каждая задача — отдельный проверяемый результат: входы, изменение, test, profiler evidence,
готовность/неизвестные. Рекомендуемый размер шага — одна механика, экран или операция
pipeline, а не «переписать весь бой» за один непроверяемый проход.

Два направления P2 и P3 после G1 могут вестись независимо при согласованных схемах.
Это порядок будущих работ, а не запуск параллельных агентов сейчас. Оценку сроков
давать после P1/P2 и одного перенесённого сложного механизма; сроки в неделях без состава
команды и опыта Rust были бы выдуманными. Наибольшая неопределённость — browser bridge,
полный UI и проверка эквивалентности, а не синтаксический перевод формул.

Если этап не проходит gate, сохранить отчёт и остановить зависимые задачи. Проверенный
Godot-выпуск продолжает существовать независимо; незавершённая Rust-ветка не становится
новым источником истины.
