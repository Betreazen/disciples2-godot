# Подготовка отряда ИИ: зелья, снаряжение, склад крепости, юниты гарнизона, лечение (24.09.2026)

Разбор `Discipl2.exe` (GOG 3.01) дизассемблером и сверка с корпусом (`20260919-human`, `20260920-legions`). Ранги: 1 —
листинг, 2 — листинг и корпус, 3 — догадка. Код: `src/D2.Data/Play/AiStackItems.cs` (решения ИИ),
`GameSession.Items.cs` (действия: выпить, надеть, снять, забрать склад — общие с окном отряда человека), правила —
`D2.Rules.Magic.Equipment` / `ItemUse` (сверены раньше харнессами Ф7). Юниты гарнизона, расстановка и лечение (§6) —
`AiStackUnits.cs`, `GameSession.Units.cs` (обмен клеток групп — им же воспользуется окно города), чистая логика —
`D2.Rules.Map.GroupArrange`. Тесты: `AiStackItemsTests`, `GroupArrangeTests`, харнесс `AiStackItemsHarnessTests`.

## 1. Где в ходе (ранг 1)

Слот `0x44` обёртки отряда `IAiStack` — «подготовка». Зовётся:

- в начале хода тактики `CAiTactic` после назначения помощников (`0x45603b`) и сборки очереди (`0x467b07`/`0x467c0e`) —
  для каждого отряда очереди по порядку (`0x465984`);
- в шаге выбора отряда (фаза 0 → 1, `0x466b68`) — при каждом выборе, в том числе повторном после исполнения.

Реализации: боец и нейтрал — `0x463863`, вор и жезлоносец — `0x464562`, призыв — пусто. Порядок у бойца:

```
в крепости: склад крепости в сумку (0x45193d)
в крепости: юниты гарнизона в отряд (0x451f5a → команда 0x41ef3a, логика на сервере 0x5d5d73)   — §6
            столица хозяина не взята (0x5e4e73): лечение и воскрешение в крепости за казну (0x451d74) — §6
вне крепости: расстановка (0x451fc4 → 0x41ef06 → сервер 0x5d57de с центровкой)                   — §6
зелья (0x451b45)
снаряжение (0x451ff3)
```

Юниты, лечение и расстановку нейтралы не делают (`0x5e5358`). У вора и жезлоносца (`0x464562`) склад обратный (`0x451a43`,
§2), остальное — то же, что у бойца, включая гарнизон, лечение и расстановку.

## 2. Склад крепости `0x45193d`

Отряд в крепости, у крепости непустой склад (`+0x70`) — весь склад в сумку отряда командой обмена `0x41f0c4`. Список
собирается множеством id (`0x524c35` → `0x525c9c`), поэтому предметы ложатся по возрастанию id (ранг 2: legions, день 6).

**Вор и жезлоносец `0x451a43`** — та же команда обмена с переставленными «откуда» и «куда»: вся сумка отряда
(`stack+0x64`) уходит на склад крепости. Сервер обмена `0x5d752e` по каждому предмету снимает его, если надет
(`0x5e746d`), и переносит (`0x5e73cb`); список — по возрастанию id. Код — `GameSession.GiveFortItems`. Ранг 2: в сохранениях
корпуса у вора и жезлоносца в крепости сумка всегда пуста (110 случаев).

## 3. Зелья `0x451b45`

При непустой сумке — по юнитам группы по порядку:

- павший (`0x5e98ad`: здоровье > 0 — жив) — первое в сумке зелье воскрешения (`0x451c50`, категория `0x837660`);
- затем, если юнит жив (в том числе только что воскрешён) и `hpMax·0,75 > hp` (`[0x6d02f0]`), — первое лечебное
  (`0x451d2d`, `0x8376f0`).

Первое — обход сумки по порядку (`0x451c97`). Команда `0x41f172`. На карте: лечебное — `min(HP_POTION, hpMax − hp)`,
воскрешение — здоровье 1 (журналы 54 из 54), зелье всегда тратится (131 из 131). Воскрешённый **лидер** заново надевает
снаряжение, и боевые слоты уплотняются: первый пуст, второй занят — второй переходит в первый (ранг 2: human, дни 21, 34,
39; после лечебного — без сдвига, дни 1, 3, 9).

## 4. Снаряжение `0x451ff3`

При непустой сумке — по семи слотам лидера (`[0x6eea00]` = 7; 0 знамя, 1 книга, 2–3 боевые, 4–5 артефакты, 6 сапоги):

```
текущий = слот; лучший = оценка(текущий)
текущий не пуст и оценка 0 → снять (0x5e746d)
по сумке: не надет нигде (0x5ec119), годен в слот (0x5df6b7 = Equipment.Check) — оценка; строго больше лучшего → он
найден другой → надеть (0x41f0fe)
после слота 2: он пуст — слот 3 пропускается; занят — его категория идёт в оценку слота 3
```

**Оценка `0x45224b`**: пусто — 0; не боевой слот — 1 (пустой слот займёт первый годный). Боевые: годны лечебное,
воскрешение, талисман, сфера (`0x5df939`, иначе код 12 — оценка 0).

| Слот 2 | Слот 3 после талисмана/сферы | Слот 3 после зелья |
|---|---|---|
| талисман: золото + 40000 | лечебное: лечит + 40000 | лечебное: лечит + 40000 |
| сфера: золото + 30000 | воскрешение: 30000 | воскрешение: 30000 |
| лечебное: лечит + 20000 | талисман: золото + 20000 | прочее: 0 |
| воскрешение: 10000 | сфера: золото + 10000 | |

«Золото» — цена предмета (`0x586a2e(…, 0)`), «лечит» — `HP_POTION` (`0x4525e0`). Талисман и сфера получают 0, если атака
предмета из классов с уроном (урон, высасывание, избыток, яд, обморожение, ожог) и её `QTY_DAM` (×3 «по всем») не больше
оценки урона лидера `0x5d2f3d` (×3, если его атака «по всем», `[0x8380c8]`) — `0x452475`.

## 5. Сверка (`AiStackItemsHarnessTests`)

«Живой день» (сохранение дня, ходы, бои, наймы, приказы из журнала; плюс предметы из мешков и `item_create` — руины,
торговцы, подарки; id нового предмета — следующий свободный). На каждом выборе отряда — подготовка портом против того,
что движок сделал с отрядом с прошлого выбора: зелья по порядку и итоговые семь слотов (надевание после выпитого зелья идёт
без `equip_check`, поэтому по командам не сверить). Перед первым выбором в ходе — ещё проход по очереди.

| | human | legions |
|---|---|---|
| окон с подготовкой | 54 | 59 |
| сошлось целиком | 45 | 43 |
| зелий журнала | 48 | 52 |

Остаток: предметы, переданные между отрядами (передача предметов ИИ и человеком харнессом не ведётся), расход боевых

## 6. Юниты гарнизона в отряд, расстановка, лечение

### Расстановка группы `0x5d57de(map, groupId, center)` (ранг 2)

Группа из одного юнита не трогается. Иначе список всех юнитов группы (лидер тоже) по порядку группы, каждый — запись
`0x5d58dd`: сила `0x5dd06c(юнит, 0, 0, 0, 3, 0)` (без брони крепости, три врага, павший — 0), ряд `0x5d59b3` (большой — 0;
малый с атакой «соседняя» `0x8380b8` класса «урон» `0x837428` — 1; прочие малые — 2), роль `0x5d5a34` (первая атака без
урона `0x5ddf70` — 2; ветка `L_SIDESHOW` `0x837f30` — 0, `L_ARCHER` `0x837f60` — 1; иначе 3). Глобали сверены по загрузчикам
`LAttR`, `LattC`, `LunitB`, `LOrder` (сравнение идёт с полем `+8` объекта категории). Список держится по убыванию силы:
вставка перед первым не сильнее (`0x5d6711`, нижняя граница по `a > b`), поэтому **при равной силе позже вставленный идёт
раньше**. Расклад в пустую схему `0x606727`:

1. ряд 0 (большие) — в первую годную клетку 0/2/4 (`0x6067fb`: большому — пустая вторая клетка колонки и передняя
   клетка; клетка пуста); не нашлось — остаётся без клетки;
2. ряд 1 — в первую годную 0/2/4; не нашлось — ждёт шага 3;
3. остальные по порядку — в первую годную 1/3/5, иначе 0/2/4.

С `center` — центровка `0x606a7b`: в переднем ряду один занятый — в 2, два — в 0 и 4 (по порядку клеток); в заднем
один — в 3, два — в 1 и 5. Перенос — обмен клеток; большой (по виду юнита в исходной клетке) тянет и вторую клетку колонки.
Применение — `CVisitorReOrderGroup` (`0x5e7991` → `0x5f4c91`): копируются только клетки, **порядок юнитов группы не
меняется**. Сохранения дня 2 (human: `S073KC0000`, `S073KC0002` с большим юнитом) совпадают с расчётом целиком.

### Юниты гарнизона в отряд `0x5d5d73(map, stackId, fortId)` (ранг 2)

Отряд должен стоять в этом укреплении. Очередь: юниты отряда без лидера (`stack+0x28`), затем гарнизона, которых можно
снять (`0x5e7a1d` с `apply = 0` → `CVisitorRmvUnitFromGroup` → у гарнизона нельзя стража `0x614568`/`0x41e1bc`), в
порядке расстановки выше. Затем выносы вперёд (`0x5d5fd8` по ряду, `0x5d6095` по роли): сила = сила первого + 1
(`[0x6ede98]` = −1), устойчивая сортировка. **Совпадение засчитывается, только если узел не первый** (`cmp eax, [[L+4]]`):
вынос ищет подходящего среди остальных. Порядок выносов: ряд 1 (не нашлось — ряд 0), роль 1 (лучник), затем при
действующем приказе `L_ASSIST`/`L_DEFEND_CITY` роль 0, иначе роль 3. Поэтому первым часто идёт не боец: у Легионов в день 1
большой `0198` обгоняет бойца `019a`, у жезлоносцев (лидерство 2) первым идёт маг, а единственный боец остаётся в гарнизоне.

Отряд расставляется без центровки; дальше каждый в очереди — `0x5d6152` — и уходит из очереди:

- у жезлоносца (способность `L_ROD`, `0x5d6469`) — не роль 2 и, при уровне сценария ≥ 10 (`0x61eb31`), не выше 1-го уровня;
- юнит уже в отряде — ничего; иначе его клетка в гарнизоне и ряд отряда: ряд 0 и 1 — клетки 0/2/4, ряд 2 — 1/3/5;
- первая пустая клетка ряда, куда годен обмен; иначе клетка, чей юнит ещё в очереди (слабее); иначе, только для ряда 2, —
  клетка переднего ряда, чей юнит в очереди вдвое слабее (`2·x < силы`);
- обмен `0x5d5642` (в журнале — `unit_transfer`, `cause = ai_reorder`) и расстановка отряда без центровки.

В конце гарнизон и отряд расставляются с центровкой. Проверка обмена `CVisitorSwapUnitPosition::canApply` (`0x61111f`):
снятие (лидер отряда не уходит, страж не уходит из гарнизона), добавление (лидер не входит в гарнизон), вместимость
`0x5f4d80`: свободные клетки + уходящие ≥ приходящие; вместимость отряда — лидерство лидера (`0x614768`, лидер считается —
у вора 1, у жезлоносца 2), гарнизона — уровень деревни или 6. Большой юнит меняется колонкой целиком: юнит второй клетки
уходит вместе с ним (human, день 1: `019c` в отряд, `01ea` и `01eb` в гарнизон). Ушедший из группы юнит выбывает из её
списка, пришедший дописывается в конец (сохранения `S073KC0000`, дни 23 и 31). «Пинг-понг» — у одинаковых юнитов отряда и
гарнизона при каждом вызове: позже вставленный гарнизонный идёт раньше и меняется с отрядным (human, день 35: 19 обменов).

**Гарнизоны в начале стратегии.** Слот 4 `CAiStrategic` (`0x44e738`, зовёт `beginTurn` `0x471a9d` после бюджета) →
`CAiStratPlayerRace` слот 2 (`0x44edee`): каждое своё укрепление без отряда-гостя (`fort+0x8c` пуст, владелец
`fort+0x84`) — расстановка гарнизона с центровкой (`0x41ef06` → `0x5d57de(…, 1)`), до наймов дня. Код —
`GameSession.AiTurn`.

**Сверка расстановки по сохранениям** (`AiGroupArrangeHarnessTests`): группа, чей состав за день не менялся, в сохранении
следующего дня стоит так, как её расставляет порт. Гарнизоны без гостя — 66 из 67 (human) и 102 из 105 (legions), отряды
вне укреплений — 520 из 540 и 656 из 665. Остаток — порядок бойцов одного ряда: сила в момент расстановки иная, чем в
сохранении (раны и гибель в боях того же дня).

Попутно: **клетка нового лидера** — 30.09 по листингу (ранг 1, `docs/ai-economy.md` §2): `CMidStack` слот 1 `0x5ebe7a` ставит в
клетку 3, в клетку 2 — при ближней первой атаке (`L_ADJACENT`) или большом воине (2 и 3); `GameSession.LeaderSlots`. Прежнее «всегда 2»
опиралось на сохранения, где свежий дальнобойный лидер уже расставлен ИИ (одиночные дальнобойные в сохранениях — стартовые отряды карты).

### Лечение в крепости `0x451d74` (ранг 1)

По юнитам отряда по порядку: павшим — воскрешение (`0x5de06e` = 0 → команда `0x41f1e6`), затем всем раненым —
лечение (`0x5de32f` = 0 → `0x41f1af`). Из кошелька тактики `CAiTactic +0x515c` (`0x586578`) вычитается `REVIVE_C` воскрешения
(`0x5de873`), а у лечения — цена, посчитанная уже после команды (`0x5de299`), то есть 0. Кошелёк читает построитель тренера
(слот `0x14` `IAiTacticInternal`, 24.09 — `docs/ai-tactic-candidates.md` §10; прежняя запись «его никто не читает» была
неверной: чтение шло через слот интерфейса, а не по смещению).

### Сверка (`AiStackItemsHarnessTests`)

Наймы в гарнизоны в этом харнессе — из журнала (`hire_unit`), стратегия порта их не делает (`BeginAiTurn(hireUnits: false)`):
иначе сверяется найм, а не перестановка. Строки журнала — переносы `ai_reorder` и лечение/воскрешение вне `ai_exec`.

| | human | legions |
|---|---|---|
| окон с юнитами | 267 | 77 |
| сошлось | 252 | 64 |
| строк журнала | 335 | 138 |

Остаток: клетки гарнизона «живого дня» (наймы сверх журнала, возвраты) и id новых отрядов расходятся с движком, у лечения —
казна и здоровье. Зелья и снаряжение human: 45 → 46 из 54 окон (юнит из гарнизона теперь в отряде, как у движка).
