# Земля карты: как движок её собирает

Разбор `Discipl2.exe` (GOG 3.01, `game-pristine`) дизассемблером capstone, 19.09.2026. Игра не
запускалась: всё ниже — из кода и данных архивов. Отправной точкой были заголовки и
переписанная процедура тулсета (`tools/d2probe/mss32/include/isoengineground.h`,
`src/isoenginegroundhooks.cpp` — перехваты там закомментированы, то есть переписанный код
не проверялся в игре). Каждое место ниже сверено с машинным кодом GOG по адресу. Где код
тулсета расходится с exe, это оговорено.

Проверка правдоподобия: по этому алгоритму на синтетической карте 14×14 (нейтральная
земля, пятна Империи, нежити, гномов, озеро) получилась картинка в стиле игры. Швов на
границах блоков 192 нет, границы рас мягкие, берег отрисован спрайтами WA. С кадром из
самой игры попиксельно не сверялось — см. «Не закрыто».

## Коротко

- Клетка — ромб **64×32**. Прямоугольник клетки `(x, y)` в мировых пикселях начинается в
  `((x − y)·32, (x + y)·16)`. Ромб задан таблицей строк (`0x6ecd08`, 32 пары
  `{x0, ширина}`): в строке `r < 16` `x0 = 30 − 2r`, ширина `2 + 4r`; строки 15 и 16 —
  `x0 = 0`, ширина **62**; дальше ромб симметрично сужается. Ромбы соседей друг на друга
  не заходят и покрывают плоскость без щелей.
- Узор 192×192 привязан к **миру**, а не к клетке. Пиксель прямоугольника клетки берётся из
  узора в точке `((X + N·64) mod 192, (Y + N·32) mod 192)`, где `(X, Y)` — мировые
  координаты пикселя, `N` — размер карты в клетках.
- Какой из вариантов `XX_00..03` взять, решается по **блокам 192×192 мира**. Таблица
  48×24 байт заполняется `rand() % 10` из MSVCRT после `srand(MAP_SEED)`, где `MAP_SEED` —
  поле сценария из `.sg`. Номер варианта — `table[блок] % число_вариантов`.
- Расы: вода → `WA` (узора нет, вода — фон), горы → **всегда `NE`**, иначе — по расе
  клетки. За картой — `BL_00`.
- Граница: на клетку накладывается узор соседа **старшего** типа через 8-битную маску
  `GrBorder NE_mm_vv`. Смешение: `dst + (src − dst)·m / 256` (в RGB565). Порядок старшинства:
  Black 0 < Water 1 < NE 2 < HE 3 < UN 4 < HU 5 < EL 6 < DW 7.
- Берег: у клетки воды, рядом с которой есть суша, сначала рисуются спрайты
  `GrBorder WA_mm_vv` (цветные, маджента прозрачна), затем поверх — суша через маски NE.
- Вариант маски (`_vv`) случаен: при создании движка земли на каждую клетку и каждую
  позицию границы бросается R250 `0..2`, берётся `% числа вариантов`. Результат живёт до
  конца сеанса и в `.sg` не пишется.
- Дороги в текстуру земли **не входят**. Это отдельные объекты карты (`CMidRoad`: `INDEX`,
  `VAR` из `.sg`), картинка — `IsoTerrn ROAD{INDEX:02}..`.
- Поверхности 128×128 — только кэш вида. Их сетка привязана к положению вида, при
  прокрутке поверхности переиспользуются. Порту эта сетка не нужна: содержимое каждого
  пикселя зависит только от мира.

## 1. Поверхность 128×128 и геометрия

`0x542547` создаёт `numX × numY` поверхностей (`CGroundTexture`, 20 байт). Размер
128 взят из `[0x6e2048]`, число — `W/128 + (W%128 > 0) + 1`. При сбросе раскладки (`0x542884`)
поверхность `(i, j)` получает `textureOffset = начало_вида + (i·128, j·128)`. При прокрутке
(`0x54272c`) поверхности, которые остались в кадре, сохраняются, а остальные получают новые
смещения и помечаются грязными. Этим и объясняются «~117 поверхностей за сеанс» и сдвиг
`st` на скролл. `render` (`0x54334b`) рисует поверхность в точке
`position + textureOffset`.

Содержимое поверхности (`0x5434bb`):

1. `0x5435da` переводит угол `textureOffset` в клетку и остаток `dst = screen(клетка) −
   textureOffset`. Клетка ищется по таблице 64×32 (переписана в тулсете как
   `textureCoordToTileCoord`).
2. Цикл идёт строками: `y` от `dst.y − 16` до `< 128` с шагом 32, `x` от `dst.x − 32` до
   `< 128` с шагом 64. На каждом шаге две клетки: `(mx, my)` в точке `(x, y)` и
   `(mx+1, my)` в точке `(x+32, y+16)`. Потом `my−1`, в следующей строке `mx+1, my+1`.
3. У каждой клетки (`0x543bbf`): `srcPos = textureOffset + dstPos + (N·64, N·32)`. Эта
   сумма, пока без остатка, хранится как `pos3` и идёт в индексатор, а сам `srcPos` берётся
   `mod 192`. Размер карты `N` берётся из `0x5a77e8` (`shl 6` / `shl 5`).
4. Клетка за картой получает запись `outOfMapBorders`, у неё тип **Black**
   (`0x541515` → `0x542f2c` пишет `[data+0x28]`). Клетка, скрытая туманом вместе со всеми
   8 соседями, заливается чёрным ромбом (`0x5ba1d0`, цвет 0). Частично скрытая клетка
   рисуется как обычно.

## 2. Узор и его вариант

**Тип клетки** (`0x5ac471`, категории — `groundcat.cpp` / `terraincat.cpp` тулсета):

| грунт | раса | тип (`TileArrayIndex`) | узор |
|---|---|---|---|
| вода | любая | Water 1 | нет, вода — фон |
| горы | любая | Neutral 2 | `NE_*` |
| равнина, лес | Нейтралы | Neutral 2 | `NE_*` |
| » | Империя | Human 5 | `HU_*` |
| » | Легионы | Heretic 3 | `HE_*` |
| » | Кланы | Dwarf 7 | `DW_*` |
| » | Орды нежити | Undead 4 | `UN_*` |
| » | Эльфы | Elf 6 | `EL_*` |
| за картой | — | Black 0 | `BL_00` |

Номера типов — это порядок создания в `TileIndices` (`0x5ab45c`): Black, Water, NE, HE, UN,
HU, EL, DW. Лес — тот же узор расы, деревья рисуются отдельным слоем (`0x5ac51d`). Число
вариантов узора равно числу картинок `XX_nn` в `Ground.ff` (`0x5ba3ef`): 4, у `BL` — 1.

**Вариант** (`CMidIsoGroundIndexer`):

```text
заполнение (0x5ae6cf), при смене MAP_SEED (кэш 0x484 = -1):
    srand(1); srand(MAP_SEED)                  # MSVCRT: srand 0x6cc1f8, rand 0x6cc2bc
    for i in 0..1151: table[i] = rand() % 10   # rand: s = s·214013 + 2531011; (s >> 16) & 0x7fff
getData(p) (0x5ae7b5):
    table[48·((p.y/192 + 24) % 24) + (p.x/192 + 48) % 48]    # деление целое, p ≥ 0
вариант = getData(pos3) % число_вариантов       (0x542bfa)
```

`MAP_SEED` берётся из `CScenarioInfo+0x74` (`0x5e3989`), в `.sg` это поле `MAP_SEED`
(`Sg.g.cs`, запись сценария). `updateData` вызывается в начале каждой отрисовки
поверхности, но таблицу пересобирает только при смене сида. Вариант один на блок
192×192 мира: таблица зациклена по 48 блокам по X и 24 по Y.

**Вырезка из 192×192** (`0x54374b…0x543b1e`, узор в ромб — `0x5b9f70`). Ромб клетки
рисуется до четырёх раз, чтобы покрыть переход через край блока:

| проход | когда | вариант берётся из точки | начало в узоре |
|---|---|---|---|
| 1 | всегда | `pos3` | `(sx, sy)` |
| 2 | `sy + 32 > 192` | `pos3 + (0, 32)` | `(sx, sy − 192)` |
| 3 | `sx + 64 > 192` | `pos3 + (64, 0)` | `(sx − 192, sy)` |
| 4 | оба условия | `pos3 + (32, 16)` ← так в коде | `(sx − 192, sy − 192)` |

`sx = pos3.x mod 192`, `sy = pos3.y mod 192`. В `0x5b9f70` строка с `src.y ∉ [0,192)`
пропускается, ширина режется до `192 − src.x`, левый край при `src.x < 0` сдвигается.
Поэтому четыре прохода делят ромб без перекрытий. **Особенность оригинала:** в проходе 4
угловой кусок берёт вариант по точке `(+32, +16)`, а не `(+64, +32)`. Если
`sx < 160` или `sy < 176`, это блок самой клетки или соседа по одной оси, а не
диагональный. Тулсет повторяет это так же. Для точного совпадения порт должен делать
так же.

## 3. Границы и берег

**Какие границы у клетки** (`0x542f39`, считается один раз при флаге `dirty`):

1. Соседи в порядке `0x6e1f58`: 0 `(−1,−1)`, 1 `(0,−1)`, 2 `(+1,−1)`, 3 `(+1,0)`,
   4 `(+1,+1)`, 5 `(0,+1)`, 6 `(−1,+1)`, 7 `(−1,0)`. За картой ставится −1: у края карты
   границ нет.
2. Собирается список типов соседей, отличных от своего, в порядке первой встречи. Для
   каждого типа `U` флаги `f[k] = (сосед k == U) и (U > свой тип)`. Младшие типы на эту
   клетку не наползают: это они получают границу от неё.
3. Классификатор (`0x543235`, `0x5432c9`, `0x5431c4`):
   - `main8` — если флаг ребра `e ∈ {1,3,5,7}` поднят, в `main8` ставятся само ребро и два
     его угла (тройки `0x6e1f98`: (1,0,2) (3,2,4) (5,4,6) (7,6,0));
   - `add8` — поднятые углы, которых нет в `main8`;
   - код = `Σ b[k]·2^k`, номер маски = индекс кода в таблице `0x6e1fc8`, 0 если его там
     нет.
   В итоге это то же, что в тулсете:
   - **основная** маска `1..15` = бит0 `(−1,0)`, бит1 `(0,−1)`, бит2 `(+1,0)`, бит3 `(0,+1)`;
   - **угловая** маска = `16 + (бит0 (−1,−1), бит1 (+1,−1), бит2 (+1,+1), бит3 (−1,+1))`, и
     только для углов, у которых оба прилегающих ребра не подняты.
4. Если `main` или `add` не равны 0, в `borders[]` добавляется запись `{U, main, add}` (до
   10 штук). Затем записи сортируются по возрастанию `U`. Сортировка переставляет
   только поля `U / main / add`. Случайные варианты (`+8`, `+0x10`) остаются за номером
   позиции в массиве.
5. Клетка воды, у которой вышла хоть одна граница: флаги `f[k] = сосед k > свой тип` (любая
   суша), по ним считаются `main` и `add` → `waterBorders`.

**Имена масок** — `GrBorder.ff`, `{префикс}_{mm}_{vv}`: `mm` — номер маски (1–15 основные,
17–31 угловые), `vv` — вариант. `createBorderTiles` (`0x5ab6fe`) грузит для **всех** типов
суши префикс `NE` (аргумент 1), для воды — `WA` (аргумент 0). Своих масок у рас нет: маска
общая, раса видна через узор. Вариантов: `NE` 1–2 на основные и 1 на угловые, `WA` 1–3.

| набор | формат (по PNG из архива) | что значит пиксель |
|---|---|---|
| `NE_mm_vv` | 64×32, 8 бит, палитра серая (индекс i = цвет (i,i,i), проверено по всем 36) | `m` — вес узора соседа: 0 нет, 255 почти весь. За ромбом тоже 255, но туда ничего не рисуется |
| `WA_mm_vv` | 64×32, RGB | маджента — прозрачно; белое — за ромбом; остальное — спрайт берега |

Ориентация проверена по картинке: у `NE_01_00` (бит0, сосед `(−1,0)`) белая кромка идёт по
верхне-левой стороне ромба. На экране сосед `(x−1, y)` стоит выше и левее, в `(−32, −16)`.

**Порядок рисования клетки** (`0x54361d`):

1. Поверхность, где есть вода:
   - при анимации воды — заливка мадженты (прозрачно), под поверхность в `render`
     кладётся анимированный фон;
   - без анимации — фон `WA_00` (или чёрная заливка, если его нет).
2. Суша: свой узор без маски (проходы 1–4).
   Вода: если есть `waterBorders`, спрайт `WA_main` и затем `WA_add` копируются в ромб
   (`0x5b9e70`: по той же таблице строк, маджента пропускается). Маски не смешиваются.
3. Для каждой записи `borders[i]` (по возрастанию `U`) — узор `U` (свой вариант блока по
   `pos3`, проходы 1–4) с маской:
   - есть обе маски: попиксельно `m = main ≠ 0 ? main : add` (буфер `0x835da0`, 2048 байт);
   - есть одна — берётся она.

**Смешение** (`0x678ba7`, RGB565):

```text
если m == 0 или dst == маджента → пропустить
для каждого канала: out = dst + floor((src − dst)·m / 256)
```

В коде сдвиг логический. Для отрицательной разности это даёт перенос в бит 24, который
отрезается при записи слова. Проверено разбором: результат для всех трёх каналов
верный. При `m = 255` узор соседа ложится почти целиком (1/256 остаётся от
исходного). Пропуск по мадженте значит, что при анимированной воде суша смешивается над
клеткой воды только там, где уже лёг спрайт берега. Без анимации под ней `WA_00`, и суша
ложится и на воду.

В `0x5b9f70` есть ветка для 16-битной маски: маджента — пропуск, `#FFFF80` — пиксель
узора, любой другой цвет пишется как есть. У ванильных масок `NE` формат 8 бит, так что в
ванили эта ветка, по всей видимости, не работает.

## 4. Вода

- Узора воды в `terrainTiles` нет: `createTerrainTiles` для Water не вызывается, у элемента
  стоит флаг `water`. `getTerrainTile` для воды возвращает `null`.
- Выбор фона (`0x5ab29c`, флаг анимации):
  - с анимацией — `waterBackground` (`0x5bb61d`, имя `WATERBKGND` — в IsoAnim);
  - без анимации — `CIsoStillBackground` из `Ground.ff WA_00` (`0x5ba5f1`: префикс 0,
    номер 0).
- `WA_00` (128×128) копируется в поверхность целиком из точки `(0,0)` (`0x5ba6fc`:
  прямоугольник `0,0,128,128`, шаг строки 256 байт). Фон воды, значит, привязан к сетке
  поверхностей, то есть к виду, а не к миру. Порту разумно положить его с периодом 128
  по миру: сдвиг сетки в оригинале зависит от того, где стоял вид при последнем сбросе
  раскладки.
- Анимированный фон `render` рисует под каждой поверхностью с водой, в той же точке и того
  же размера (`0x5433ee`).

## Дороги

`IsoTerrn ROAD0000..ROAD1500` — 16 картинок 62×32 (ширина как у широкой строки ромба). В
`CGroundTexture::draw` дорог нет. Дорога — объект `CMidRoad` из `.sg` (`ROAD_ID`,
`INDEX`, `VAR`, позиция). `0x5bc10d` берёт байты `+0x1c` (индекс) и `+0x1d` (вариант) и
вызывает `0x5c2231`. Та ищет картинки с префиксом `ROAD%02d` и берёт `VAR % их_числа`.
Картинка идёт в список изображений слоя (`0x524c10`). Индекс — 4-битная маска соседних
дорог (16 картинок). Сама маска хранится в `.sg`, движок при отрисовке её не считает.

## Для порта

- Земля рисуется по клеткам, без сетки 128: ромб 64×32, `srcPos` по миру, вариант из
  `table[блок]`, до 4 проходов с особенностью прохода 4, маски NE со смешением, спрайты
  WA на воде.
- Данные на входе: `.sg` (`MAP_SEED`, грунт и раса из блоков `MidgardMap`, дороги),
  `Ground/*`, `GrBorder/*`, `IsoTerrn/ROAD*`, у воды — `WA_00` или анимация.
- Случайный вариант маски детерминированно не восстановить: R250 при создании вида
  зависит от всего, что брало числа до этого. Для совпадения «как в оригинале»
  достаточно любого равномерного `0..2` на клетку и позицию. Попиксельная сверка с кадром
  игры будет расходиться только на кромках с масками, у которых больше одного варианта.
- Цвет: смешение в оригинале идёт в RGB565, в 8 бит на канал результат может отличаться
  на единицу младшего разряда.

## Не закрыто

- Попиксельной сверки с кадром игры нет. Нужен снимок карты с известным `MAP_SEED` и
  координатами прокрутки; интерфейс знает пользователь. Сверять удобнее всего клетки без
  границ: там случайности нет.
- Анимированная вода: формат `WATERBKGND` в IsoAnim (кадры, размер, скорость) не
  разбирался.
- Место картинки дороги в клетке (смещение от угла прямоугольника) не проверено: слой
  `0x524c10` не разбирался.
- Флаг анимации воды (`0x5ab29c`, `[0x838524]`): откуда он берётся (настройка? по
  соседству в строках есть `TOG_PLAYAIISOANIM`), не выяснено.
- Если в `.sg` тип клетки вне таблицы (неизвестная раса), берётся `NE` — это видно из кода
  (ветка по умолчанию `0x5ac517`), игрой не проверялось.

Модель, по которой рисовалась синтетическая проверка, — временный скрипт
`render.py` (numpy + PIL) в каталоге подагента, в репозиторий не клался. Весь алгоритм
записан выше.
