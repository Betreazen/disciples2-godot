# Схема корпуса зонда (версия 7.5)

Источник истины — код зонда: `tools/d2probe/mss32/src/probehooks.cpp` (какие поля
пишет каждый хук), `tools/d2probe/mss32/src/probeecon.cpp` (казна, объекты карты,
предметы, город, вор — схема 5), `tools/d2probe/mss32/src/probediplo.cpp`
(дипломатические отношения — схема 5.2), `tools/d2probe/mss32/src/probespend.cpp`
(причины трат казны — схема 5.3), `tools/d2probe/mss32/src/probemap.cpp`,
`probecheck.cpp`, `probenoble.cpp` (схема 6.0, партия 1: сохранение, укрепления, земля,
ход, проверки интерфейса, воры, союзы), `probeleader.cpp` (6.0, партия 2), `probehit.cpp`
(схема 6.1: цель атак без урона), `probestate.cpp` (схема 6.2: пересев генератора, запас хода),
`probeunit.cpp` (схема 6.3: перенос юнитов, отказы интерфейса), `probeai.cpp` (схема 6.4: ход ИИ на
карте), `probeaieco.cpp` и `probeaitac.cpp` (схема 6.5: экономический шаг и тактика ИИ), `probeui.cpp`
(схема 7.0/7.1: экраны, нажатия, тексты интерфейса, окна сообщений, новая игра / загрузка / выход),
`probeai72.cpp` (схема 7.2: кэш целей тактики, сила по юнитам, лечение, повышение, A*, выдача id),
`probeairng.cpp` (схема 7.5: места бросков `ai_rng`),
`tools/d2probe/mss32/src/probeinput.cpp` (журнал ввода)
и `tools/d2probe/mss32/src/probe.cpp` (обёртка `{"seq":...,"tid":...,"t":...,...}`,
счётчики `rng`/`rng_std`). Подробное описание режима зонда — `tools/d2probe/README.md`,
раздел «Режим зонда». Эта схема — производная документация; при расхождении с кодом
прав код, схему нужно поправить вслед за ним и поднять версию.

Версия 2 (05.09.2026, коммит зонда `7c11f9c`) относительно версии 1:

1. `battle_start` теперь пишется в `beforeBattleRound` (при первом вызове на бой) и
   **не несёт идентичности** (`type`/`level`/`hp_max`) — `objectMap` там физически
   недоступен. Идентичность вынесена в новое событие `battle_units`.

   > **Поправка 08.09.2026 по живому прогону `corpus/20260908-f6`: «при первом вызове на бой»
   > неверно — `battle_start` пишется ПЕРЕД КАЖДЫМ РАУНДОМ.** На три боя пришлось 13
   > `battle_start` против 3 `battle_end` и 16 `round`. Картина одного боя: `battle_start`
   > с `round = 0` **дважды** (это известное «beforeBattleRound на первый раунд зовётся
   > дважды»), затем по одному `battle_start` с `round = N` перед каждым следующим раундом.
   >
   > Почему дедуп не сработал: метку `firstTimeSeen(currentBattle, …)` сбрасывает конструктор
   > `BattleMsgData` (`battleMsgDataCtorProbe` → `forgetBattle`), а конструктор, как честно
   > сказано в комментарии рядом с ним, «работает и на копиях» — движок конструирует копию
   > между раундами, метка слетает, и строка пишется снова.
   >
   > **Зонд ради этого не переделываем: данные не испорчены, а даже богаче** — снимок `units[]`
   > достаётся на каждый раунд. Но читать корпус надо правильно: **бой сегментируется по
   > `battle_end`, а не по `battle_start`**, число боёв равно числу `battle_end`, а
   > `battle_start` с наибольшим `seq` перед данным `battle_end` — это последний раунд боя,
   > а не его начало.
   >
   > **Читатель это уже делает, и теперь это закреплено тестом** (задача 14 Ф6):
   > `CorpusReader.Battles` закрывает бой только по `battle_end`, а `battle_start` при уже
   > открытом бое с тем же набором id юнитов оставляет событием того же боя. Проверка —
   > `D2.Data.Tests/SchemaV4CompatTests.V4Journal_BattleCountEqualsBattleEndCount_NotBattleStart`:
   > 13 `battle_start` и 3 `battle_end` дают ровно 3 боя, все с `End != null`, и ни одна
   > лишняя строка `battle_start` не теряется.
2. `rng`/`rng_std` пишутся только пока бой активен (окно `[battle_start, battle_end]`);
   сами счётчики `n` растут всегда, так что `rng_before`/`rng_after` у `miss`/`dmg` могут
   ссылаться на броски, сделанные вне какого-либо боя и потому невидимые в журнале.
3. `crit` в `dmg` уточнён как входной аргумент, не результат (см. таблицу ниже) —
   само поле не переименовано, значение в журнале как было, так и есть всегда `true`.
4. Пустые слоты боя (`unitsInfo`/`turnsOrder`) больше не пишутся вовсе — раньше они
   утекали в журнал как юнит с `id:"INVALID-ID"`.

## Общие поля

Есть в каждой строке:

| Поле | Тип | Что это |
|---|---|---|
| `seq` | int64 | Монотонный номер события, взят **до** вызова оригинала (кроме `battle_end`, см. ниже). Файл **не отсортирован** по `seq` — вложенные вызовы (например, `dmg` внутри себя зовёт `dmg_buffs`, `armor`, `power`) пишут свою строку раньше внешнего события, у которого `seq` меньше. |
| `tid` | int64 | `GetCurrentThreadId()` потока, из которого пришёл вызов. |
| `t` | int64 | **Схема 5.** Миллисекунды с открытия журнала (`GetTickCount64`, засечка в `probe::init`). Стена времени этого нуля — в имени файла (`ГГГГММДД-ЧЧММСС-<pid>.jsonl`). **В журналах схем 2.1–4 поля нет**: читатель обязан считать его необязательным. |
| `ev` | string | Тип события. |

`rng` и `rng_std` — раздельные монотонные счётчики `n` (первый — движковый генератор
`0x54851f`, второй — CRT `rand`, `0x548576`). В `rng_before`/`rng_after` событий `miss`
и `dmg` входит только счётчик `rng`, не `rng_std`. Счётчики растут всегда (пока журнал
открыт), но сама строка `rng`/`rng_std` пишется **только пока бой активен** — окно
`[battle_start, battle_end]` включительно (флаг `probe::setBattleActive`, `probe.cpp`).
Из этого следует: `rng_before`/`rng_after` у `miss`/`dmg` вне боя (или в интервале,
захватывающем момент вне боя) могут указывать на броски, для которых в журнале нет
соответствующей строки `rng` — счётчик тикнул, а строка не попала в файл.

### Почему «по ключу», а не «писать всё» и не «первые N»

`computeMovementCost` зовётся поиском пути на каждую клетку-кандидат — за одно движение
мыши это тысячи вызовов, и запись каждого делает журнал бесполезным. Бюджет («первые N
строк») запрещён правилом репозитория: частый случай выест бюджет и спрячет редкий.
Режим записи — строка на **новое сочетание признаков**, а рядом счётчик **без бюджета**,
который печатается событием `counts`. Тогда «`move_cost` встретился 41 273 раза,
уникальных сочетаний 118» — проверяемое утверждение, а не пустой лог.

Читатель журнала обязан помнить: у keyed-события число строк — это число **уникальных
сочетаний**, а число вызовов лежит только в `counts.calls`. Считать вызовы по строкам
нельзя.

То же правило действует и для keyed-событий версии 4 (`immune`, `attack_get`): их
счётчики без бюджета лежат в том же `counts.calls`.

У множества ключей стоит потолок (`keyCapOf`, `probe.cpp`): ключ `move_cost`
несёт координаты, отряд, шесть флагов и результат и в принципе неограничен, а без потолка
за длинный прогон это сотни тысяч строк в куче. До схемы 7.4 множество было **одно на прогон**
с потолком 200 000 на все виды; с 7.4 у каждого вида своё множество и свой потолок
(`move_cost` — 200 000, с 7.5 — 1 000 000 хешей ключей; прочие — 20 000), а при входе в партию (строка `game_phase`) все ключи
забываются (раздел «Схема 7.4»). Ключ сверх потолка не запоминается и
**не даёт строки**, а считается отдельно — `counts.keys_dropped` (с 7.4 и по видам —
`counts.keys_dropped_by`). Счётчики `calls` при этом
остаются точными: потолок режет выборку сочетаний, а не учёт вызовов. `keys_dropped > 0` в
журнале означает, что список уникальных сочетаний неполон, — это надо видеть, а не гадать.

Строка `counts` при выгрузке DLL берёт оба замка **без ожидания** (`try_to_lock`). Штатный
выход из игры — `ExitProcess`: Windows сначала убивает прочие потоки, а `DllMain` зовёт
после, под loader lock; поток, убитый внутри `emit()`, оставил бы замок журнала занятым
навсегда, и блокирующее ожидание повесило бы выход из игры. Поэтому при занятом замке
финальная строка `counts` просто не пишется: потерянное наблюдение дешевле повисшего
прогона. Строки `counts` на смену дня это не касается — там игра жива.

### Опознание атаки (`attack`, `class`, `source`)

Три поля пишутся одинаково во всех трёх событиях выше и берутся из `IAttack`:

| Поле | Что это |
|---|---|
| `attack` | `IAttack::id` — id атаки из `Gattacks`. `"null"`, если атаки нет (движок вернул `nullptr`). |
| `class` | `LAttackClass::id` — класс атаки (`attackclasscat.h`, `AttackClassId`). `-1`, если атаки нет. |
| `source` | `LAttackSource::id` — источник атаки (`attacksourcecat.h`, `AttackSourceId`). `-1`, если атаки нет. |

В `attack_new` есть ещё `disp_class` — это `LAttackClass`, **переданный аргументом** в
`createBatAttack`, то есть класс, по которому движок выбирает реализацию действия.
Обычно совпадает с `class`; расхождение значит, что движок диспетчеризуется на
альтернативной атаке. Само поле `attack` в `attack_new` получено вызовом
`getAttackById(objectMap, impl, number, checkAltAttack = false)` — то есть это **основная**
атака импла; альтернативную читатель при расхождении разрешает из данных по `impl`
и `number`.

`target_group` в `attack_new` — id группы, по которой атака может бить (свои или
враги), спрошенный у созданного объекта `IBatAttack::getTargetGroupId`. Объект
принадлежит вызывающему коду и зондом не уничтожается. Когда `battleMsgData` нет,
поле выходит пустым id — не выдуманным.

### Земля игрока (`terrain_day`)

Клетка принадлежит расе, чей террейн на ней лежит; `terrain` — `TerrainId`
(`categoryids.h:299`), полученный из расы игрока тем же отображением, что и в движке
(`hooks::getTerrainCategory`, `gameutils.cpp:364`). `race` — `RaceId` игрока,
`size` — `CScenarioInfo::mapSize`, `owned` — сколько клеток этого террейна на карте.

`cells` — те же клетки в компактном RLE по строкам:

```
"cells":"20:22-25;21:21-26,30;22:20"
```

Читается так: строка `y=20` — колонки 22..25; строка `y=21` — колонки 21..26 и 30;
строка `y=22` — одна колонка 20. Отрезки внутри строки разделены запятой, строки —
точкой с запятой, обе координаты возрастают. Отрезок из одной клетки пишется одним
числом, строки без своих клеток не пишутся вовсе, пустая карта даёт `"cells":""`.
Формат выбран из-за объёма: на карте С4 это сотни клеток в день на игрока, и список пар
был бы на порядок длиннее того же содержания.

Когда сценарий, игрок или его раса не читаются, строка всё равно пишется, но
`race`/`terrain`/`size`/`owned` равны `-1`, а `cells` пуст — выдуманных чисел в журнале
нет. Счётчик `counts.calls.terrain_day` при этом всё равно тикает.

`terrain_day` — не хук, поэтому его имени нет в `start.hooks`. Выключить обход карты
всё же можно: в `probe/hooks.txt` он подчиняется имени `terrain_day` по тем же правилам,
что настоящие хуки (нет файла — включён). Это нужно для бисекции: обход карты —
самое тяжёлое, что зонд делает, хотя и только на чтение.

### Как названы ид-поля

Аргументы серверных обработчиков — указатели на `CMidgardID`, и роль каждого по
позиции в общем случае **не доказана**. Поэтому имя поля берётся **из самого id**: две
буквы на позиции 4 строкового вида (`"S143SI0000"` → `SI`) — это тип объекта.

| Код | Поле | Код | Поле | Код | Поле |
|---|---|---|---|---|---|
| `SI` | `site` | `KC` | `stack` | `UN` | `unit` |
| `IM` | `item` | `IG` | `item_type` | `SS` | `spell` |
| `UU` | `unit_type` | `PL` | `player` | `FT` | `fort` |
| `BB` | `building` | `NA` | `action` | `RU` | `ruin` |
| `RD` | `rod` | `BG` | `bag` | `TB` | `tomb` |
| `SR` | `subrace` | | | | |

Тип, которого нет в таблице, и **повторный** тип в том же вызове пишутся как `idN`, где
`N` — номер аргумента (первым идёт не `objectMap`, а первый ид-аргумент). Так два отряда
в одном вызове остаются двумя разными полями, а не схлопываются.

Указатель, по которому нельзя прочитать четыре байта (аргумент оказался целым числом, а
не идом), даёт `"null"` и **никогда не роняет игру**: перед разыменованием стоит проверка
`VirtualQuery` (`probeecon.cpp`, `readable()`). Это цена честности: позиции, не
доказанные дизассемблированием, не выдаются за доказанные.

Зеркальное правило: как только позиция **доказана**, поле называется по смыслу, а не по типу
id. Первый такой случай — `thief_roll` схемы 5.1: `action` и `target` вместо `id1` и `stack`
(см. «Бросок вора»). Общее правило выше — для всего остального, где роли аргументов не читаны.

### Бросок вора (`thief_roll`)

Формула, прочитанная по адресам `0x4430ae`–`0x4430c1`:

```
успех  ⇔  (rand(0..99) + rand(0..99)) / 2  ≤  порог
```

Бросок **треугольный**, а не плоский, и оба слагаемых идут через движковый генератор
(`0x54851f`), тот же, что пишет событие `rng`. С версии 5.1 в строке лежат сами кубики
(`dice1`, `dice2`) и порог (`chance`), так что каждое наблюдение — не неравенство, а
равенство: `dice1`, `dice2`, `chance` и `ret` проверяются друг о друга целиком.

**Откуда берутся кубики.** Строки `rng` пишутся только пока активен бой, а вор работает
на карте приключений — значит, ни один бросок вора в `rng` не попадает (проверено: у
четырнадцати бросков первой большой партии искали `rng` с номерами `rng_before+1` и `+2`
и нашли 0 из 28). Поэтому зонд запоминает **последние четыре** выданных генератором
значения независимо от боя (`probe::rngResultAt`, `probe.cpp`), а обёртка спрашивает у
кольца именно вызовы `rng_before+1` и `rng_before+2`. Кольцо, а не «последние два»:
поиск идёт по номеру вызова, поэтому взять чужой, более поздний бросок нельзя. Если
значение по какой-то причине не нашлось, поле равно `-1`.

**Откуда берётся порог.** Оригинал первой же строкой (`0x443080`) зовёт `0x5d31a1` —
она и считает порог:

```
chance = globalData->actions[action]        ; поле +0x10 записи, то есть Gaction.CHANCE
если chance < 100 и цель — отряд (тип id 0x23) либо укрепление (0x1d):
    chance -= сопротивление цели
если chance < 0: chance = 0
```

Результат возвращается по значению (скрытый первый аргумент, `ret 0x10`), оригинал
читает его тривиальным геттером `0x566368` (`mov eax,[ecx]; ret`) и сравнивает с
броском. Порог — локальная переменная оригинала и из обёртки `thief_roll` не виден,
поэтому зонд ставит **второй хук**, `thief_chance` (`0x5d31a1`), и читает то самое
число, которое функция записала. Повторный вызов `0x5d31a1` из обёртки был бы короче,
но заново исполнял бы движковый код с `dynamic_cast` и виртуальными вызовами — зонд не
должен уметь уронить живой прогон, а наблюдение не исполняет ничего.

Вызывающих у `0x5d31a1` ровно два (проверено сканированием `.text` на `E8`/`E9`): сам
бросок (`0x443080`) и интерфейс (`0x49b446`), который показывает шанс игроку. Чтобы в
строку не попал показанный игроку порог от постороннего вызова, зонд берёт значение
только когда счётчик `thief_chance` сдвинулся за время вызова оригинала **ровно на
единицу**; иначе `chance = -1`. Счётчик `counts.calls.thief_chance` — без бюджета:
`thief_chance` = 0 при ненулевом `thief_roll` читается как «хук не встал», а не как
«порог не достался».

**Что значат `action` и `target`.** Разобрано по машинному коду, а не по позиции
аргумента:

| Поле | Что это | Чем доказано |
|---|---|---|
| `action` | `LNobleActionCat::id` — категория действия вора (`nobleactioncat.h`: 0 PoisonStack, 1 Spy, 2 StealItem, 3 Assassinate, 4 Misfit, 5 Duel, 6 PoisonCity, 7 StealSpell, 8 Bribe, 9 StealGold, 10 StealMerchant, 11 StealMage, 12 SpyRuin, 13 RiotCity) | `0x5d31a1` ищет по этому указателю запись в `globalData->actions` (`+0xa8`, `0x5945d3`) и проверяет у него поле `+4` (таблицу категории) на ноль |
| `target` | Id **цели**: отряд (`KC`) или укрепление | `0x5d31a1` зовёт по этому указателю `CMidgardID::getType` (`0x57f3b6`) и сравнивает тип с `0x23` (отряд) и `0x1d` (укрепление), после чего вычитает сопротивление цели |

До версии 5.1 оба аргумента писались как id по общему правилу «имя поля из самого id»,
и оба имени были неверны: у категории читались первые четыре байта — её vftable, отчего
поле `id1` во всех четырнадцати бросках первой большой партии равнялось одному и тому же
`G001CRedb4`; а цель попадала в поле `stack` и читалась как вор, хотя четыре броска из
четырнадцати называли отряд нейтралов (`ORDER = 2`, страж), который воров не водит.
**Вора в аргументах броска нет вовсе** — он остался у вызывающего (`0x442fe1`).

## Дипломатические отношения (`relation`)

Появилось в версии 5.2, живёт в `tools/d2probe/mss32/src/probediplo.cpp`. Адрес — сборки
**Gog** и лежит в том же файле (по той же причине, что адреса схемы 5, см. выше); на
остальных сборках хук не ставится.

|---|---|---|---|---|

| `changed` | **Все** пары, у которых слово `RELATION` за вызов изменилось: `[{"race1", "race2", "before", "after"}]`, `before`/`after` — сырые слова (`-1` в `before` — пары до вызова не было). Основная пара тоже здесь, если сдвинулась. |
| `ret` | Ответ мутатора. |

Перед разыменованием каждый указатель проходит `probe::readable` (`VirtualQuery`), как у
хуков схемы 5: неверная позиция даёт `"null"`/`-1`/`null`, а не падение живого прогона.

**Сигнатура**, прочитанная по `game-pristine/Discipl2.exe`: пролог `__EH_prolog`, аргументы
`[ebp+8]`…`[ebp+0x18]`, выход `ret 0x14` (`0x5d959b`).

```
bool __stdcall changeRelations(IMidgardObjectMap* map, const CMidgardID* playerA,
                               const CMidgardID* playerB, int value, bool absolute)
```

**Что делает** (`0x5d9366`–`0x5d959b`):

```
если A == B: вернуть true                                  ; 0x5d937b
для каждого игрока X карты, X != B:                        ; 0x5d9428
    если у (X, B) вечная война (бит 30): пропустить          ; 0x5f7977
    если X == A:  setRelation(A, B, absolute ? value : rel(A,B) + value)
    иначе, если rel(X, B) <= D_WAR:                           ; 0x5f7d94
                  setRelation(A, X, rel(A,X) − value/2)       ; деление к нулю, 0x5d953f
вернуть true
```

`setRelation` (`0x5d959e`, единственный вызов — `0x5d9551`) обрезает значение в `[0, 100]`
и сразу применяет визитор `CVisitorDiploCurrent` (vftable `0x6f0c5c`) режимом 1 через
`0x5e68af`, а тот зовёт `CMidDiplomacy::setCurrentRelation` (`0x5f799c`): меняются только
биты 1…7, при вечной войне запись отменяется. Запись синхронна — `after` и `changed`, снятые
сразу после возврата, её уже видят.

**Правило третьей стороны — внутри того же вызова**, отдельного вызова мутатора для него нет.
Поэтому хук и снимает весь список пар до и после: третьи стороны — элементы `changed`,
отличные от пары (`race_a`, `race_b`), вида (`race_a`, X). Пара третьей стороны, у которой
значение упёрлось в прежнее (0 → 0, 100 → 100), в `changed` не попадает: слово не изменилось.

**Адрес возврата → причина.** Мутатор зовут ровно девять мест (сканирование `.text` на
`call`/`jmp rel32` и на `imm32` адреса — других ссылок нет), каждое в своей обёртке с одним
чтением `GVars` (смещения геттеров: `D_WAR +0xbc`, `D_NEUTRAL +0xc0`, `D_GOLD +0xc4`,
`D_MK_ALLY +0xc8`, `D_ATTAK_SC +0xcc`, `D_ATTAK_FO +0xd0`, `D_ATTAK_PC +0xd4`, `D_ROD +0xd8`,
`D_BK_ALLY +0xdc`, `D_REF_ALLY +0xe0`, `D_NOBLE +0xe4`). Эффект, из которого зовётся обёртка,
опознан по RTTI vftable его метода; «=» — присваивание (`absolute = 1`), «+» — прибавление.

сценарное событие или чит; ввод чита виден в журнале ввода (`input`) как набранные клавиши.

## Причины трат казны

Появились в версии 5.3, живут в `tools/d2probe/mss32/src/probespend.cpp`. Адреса — сборки
**Gog** (`game-pristine/Discipl2.exe`, ImageBase `0x400000`) и лежат в том же файле; на прочих
сборках хуки не ставятся.

### Кто двигает казну

Каждое движение казны идёт через помощник `0x5e6920` (`__stdcall`, `ret 0x10`: игрок, новая
казна, карта, `apply`): он строит `CVisitorChangePlayerBank` (`0x60bde3`) и применяет его —
отсюда строка `bank`. Второй кошелёк `CMidPlayer::spellBank` (`+0x7c`) двигает близнец
`0x5e69b3` — визитор режима 1; у него два вызова: дневной доход ИИ (`0x43ae49`) и заклинание
со второго кошелька (`0x5dc3ed`). Сканирование `.text` даёт у `0x5e6920` 27 вызовов; кто зовёт,

### Порядок относительно `bank`

Как у `site_*`: причина берёт `seq` **до** вызова оригинала, а строку пишет **после** — поэтому
её `bank` имеет больший `seq`, но в файле стоит **раньше** строки причины. В отличие от
`site_*`, «`bank` = `seq + 1`» здесь не гарантировано: проверки внутри вызова тоже берут номера,
а ключевые строки пишутся не на каждый вызов (в корпусе `20260910-passive/passive-002.jsonl`
у найма в столице между строкой `build_status` 70317 и `bank` 70326 — разрыв в 9 номеров).
Сопоставлять — по игроку и интервалу (`seq`, `seq_end`). Сколько строк `bank` внутри:

| Событие | Строк `bank` при `ret = true` |
|---|---|
| `hire_unit`, `hire_leader`, `rod_drop`, `wand_cast` | ровно одна, `mode 0` |
| `spell_research` | одна, `mode 0`; при `free = true` — ни одной |
| `spell_cast` | ни одной при `free = true` или неиграбельной расе игрока (`0x5e5358`, нейтралы); одна `mode 0` обычно; **две** при `use_spell_bank = true` и нехватке основной казны: сначала `mode 1` (второй кошелёк: `spellBank − (цена − казна)`), затем `mode 0`, **обнуляющая основную казну целиком, золото тоже** |

### Сигнатуры и что движок делает с каждым слотом

Все прочитаны по машинному коду: ширина `ret`, слоты `[ebp+8]…` и то, куда движок их передаёт.

- **`hire_unit`** — `bool __stdcall (map, playerId, unitTypeId, const char* name, groupId, int
  position)`. Проверка `0x5deea7` с теми же слотами; цена — слот `+0x54` импла, найденного в
  таблице юнитов по `unitTypeId` (`Gunits.ENROLL_C`, `sites.md`); списание `0x5e6920` по
  `playerId`; `AddUnitToGroup` `0x5e78f7` (`unitTypeId`, `groupId`, `position`); группа —
  `GetStackFortRuinGroup` `0x5f4f87`. `name` уходит в `0x5e768f` и не пишется.
- **`hire_leader`** — `bool __stdcall (map, playerId, fortId, unitTypeId, const char* name,
  order, orderTarget)`. Проверка `0x5de921` (`map`, `playerId`, `unitTypeId`); цена и списание —
  как у юнита; новый отряд — `0x5e6e43` (`unitTypeId`, `fortId`); `fortId` движок приводит к
  `CFortification` (typeinfo `0x78ce10`) и берёт его отряд. Имя и слоты приказа (`0x5e811a`) не
  пишутся.
- **`rod_drop`** — `CEffectDropRod::apply(map, …)`, поля эффекта: отряд `+4`, клетка `+8`
  (два `int`). Проверка `0x5d9e59` (отряд, клетка, карта), трата хода `0x5e780d`, цена
  `GVars.ROD_COST` (`0x587851`), списание по владельцу отряда, `CVisitorCreateRod` `0x5e86ef`.
- **`spell_cast`** — `bool __stdcall (map, playerId, spellId, const CMqPoint* position,
  useSpellBank, free)`, оба флага движок сравнивает байтом. Проверка `0x5dbd75`; при
  играбельной расе и `free = 0` — оплата `0x5dc334` и запись каста `0x5dc481`. Цена —
  `Gspells.CASTING_C` (`0x582afa`, данные заклинания `+0x34`). Флаг `use_spell_bank` ставит
  эффект (`CEffectSpell +0x14`), `free` — `+0x15`.
- **`spell_research`** — `bool __stdcall (map, playerId, spellId, free)`. Проверка `0x5dbf3d`;
  при `free = 0` цена — `0x604039`: **`GspellR.RESEARCH` для лорда игрока**
  (`CMidPlayer +0x28` → таблица лордов `0x580c36` → `0x58b6d2` по `spellId`), у лорда категории
  `[0x837760]` — **пополам** (`0x5867f0`); не хватает — `false` без списания. Затем заклинание
  добавляется игроку (`0x5e6afc`). **Это и есть 13 трат маны харнесса, не равных `CASTING_C`**:
  по сумме все они совпадают с `RESEARCH` или `RESEARCH / 2` (`786453`: 400/800/400 —
  `RESEARCH`; `1338325` — `RESEARCH / 2`), а с `Gspells.BUY_C` (цена башни мага) — ни одна.
  Суммы исследования, применения и посоха в ванили часто совпадают, поэтому отличает их только
  событие.
- **`wand_cast`** — `bool __stdcall (map, playerId, targetId, ownerId, itemId, const CMqPoint*
  position)`. Проверка `0x5dbdd2` (`itemId`, `targetId`, клетка): у `targetId` движок берёт
  владельца (`0x5f501a`). Цена — слот `+4` заклинательного расширения предмета (`0x407b7e`;
  по имени поля — `GItem.CASTING`, ранг 2); не хватает — `false`; списание `0x5e6920`; отметка
  применения `0x5e7f59`; расходуемый предмет (слот `+0xc`) уничтожается из инвентаря `ownerId`
  (`DestroyItem` `0x5e737d`). `item` и клетка снимаются до вызова.

Счётчики `counts.calls` шести событий — без бюджета: ноль — «хук стоял и путь не звался»,
встал ли хук — поле `hooks` строки `start`.

**Как читать.** Причина — по `ret_addr`, а не по соседним событиям журнала: одна строка — одно
решение движка, `changed` — его полный след на всех парах. Счётчик `counts.calls.relation` —
без бюджета: `"relation":0` — «хук стоял и мутатор не звался», а встал ли хук, видно в поле
`hooks` строки `start`.

## Схема 6.2: пересев генератора (`rng_seed`) и запас хода (`ap_restore`)

Появилась 17.09.2026, живёт в `tools/d2probe/mss32/src/probestate.cpp` (`hooks::addStateHooks`). Адреса —
`game-dev/Discipl2.exe` (GOG 3.01), capstone.

### `rng_seed`

**Кто пишет состояние генератора.** Индекс `0x838c24` и таблицу `0x7b4978` (250 слов) пишут ровно три места —
это все ссылки из `.text` на оба адреса и на диапазон таблицы: шаг `0x67819c`, его инлайновая копия в `0x6781dd`
и `setState` `0x67816c` (`index % 250`, копия 250 слов, `ret 8`). `setState` зовёт только `0x548473` — та же
функция под критической секцией `0x836fd8` (`InitializeCriticalSection` в статическом конструкторе `0x548409`),
`__stdcall(index, table)`, `ret 8`, пролог `mov eax, 0x6ab968` / `call 0x66bd10`. Её вызывают двое:

| Вызов | Где | Что | `via` | `cause` (возврат) |
|---|---|---|---|---|
| `0x548500` | `reseed` `0x5484bd`, `__stdcall(seed)`, `ret 4` | `getState` `0x548429` в локальный буфер, затем `setState(seed, буфер)` — меняется только индекс | `reseed` | по адресу возврата `reseed`, ниже |
| `0x429de7` | `0x429d3b` — открытие сценария (зовут `0x422b4e`, новая игра, и `0x43378a`, `CMidServerBuilderFull`) | загрузка: `setState(scenario+0x669, scenario+0x66d)`, таблица из сохранения | `set_state` | `load_save` (`0x429dec`) |

`reseed` вызывают `0x429dc8` в той же `0x429d3b` (`reseed(timeGetTime())`, ветка новой игры: `new_game_time`,
`0x429dcd`) и `0x61b8c4` в `0x61b89c` ← `0x40224f` (`reseed(таймер CUIManager, 0x5613e1)`: `reseed_ui_timer`,
`0x61b8c9`). Чтение `getState` `0x548429` зовут `0x5484f1` (внутри `reseed`) и `0x42a017` (запись сохранения) —
событий не дают. Инициализации таблицы кодом нет: 250 слов и индекс 47 — данные образа.

Хук стоит на `0x548473`; хук `rng_reseed` на `0x5484bd` только запоминает (в `thread_local`) свой адрес возврата,
чтобы `rng_seed` назвал внешнюю причину. Снимок до и после берётся под той же критической секцией (рекурсивной —
оригинал входит в неё ещё раз), строка пишется уже без неё.

| `ev` | Поля сверх общих | Типы | Пишется |
|---|---|---|---|
| `rng_seed` | `n`, `arg`, `index_before`, `index_after`, `via`, `cause`, `ret_addr`, `wide`, `table` | int64×4, string×3, int64, string | **Каждый вызов** `0x548473` (единицы за прогон; без ключа и бюджета). `n` — счётчик вызовов `generateRandomNumber` на момент записи, тот же, что у строки `rng`: следующий бросок будет `n + 1` (при отключённом хуке `rng` счётчик стоит на нуле). `arg` — аргумент-индекс до `% 250` (у пересева — зерно). `index_before`/`index_after` — `0x838c24` до и после. `via` — `reseed` (адрес возврата `0x548505`) или `set_state`. `ret_addr` — внешний адрес возврата (у `reseed` — его собственный), `cause` — по нему, иначе `unknown`; `reseed_unhooked` — путь через `reseed`, но хук `rng_reseed` выключен в `hooks.txt` (внешний адрес неизвестен, `ret_addr` = `0x548505`). `table` — 250 слов после записи по 4 шестнадцатеричных знака (младшие 16 бит) без разделителей, 1000 знаков. `wide` — сколько слов не влезло в 16 бит (ожидается 0; иначе `table` неполна). |

**Как пользоваться.** Генератор сразу после строки `rng_seed` — это `table` и `index_after`; до броска с номером
`m` из строки `rng` проходит `m − n − 1` вызовов (и сколько-то лишних шагов на отбраковку, см. `docs/re-rng.md`).
Читатель: `RngSeedEvent.Table` (`IReadOnlyList<ushort>`).

**Поправка 7.1, часть 3 (28.09).** `load_save` при обычных настройках не бывает: ветки `0x429d3b` выбирает флаг
`GameSettings::random` (`Disciple.ini` «Random»), и при нём загрузка генератор не трогает. Состояние на открытии
сценария — строка `rng_state`, раздел «Схема 7.1, часть 3».

### `ap_restore`

**Кто пишет запас хода.** Байт `CMidStack::movement` (`+0x98`) в `.text` пишут две инструкции (скан всех
операндов `[reg+0x98]` размером в байт): `0x5ebfbe` (`CMidStack::initialize`, `ret 0x14` — создание отряда) и
`0x5ecfd5` (`CVisitorChangeStackMoveAllowance::apply` `0x5ecf76`: `movement = clamp(movement + delta, 0, MOVE
лидера)`, где `delta = −amount`, `neg ecx` `0x60d30b`). Визитёр строит только `changeStackMove` `0x5e780d`,
`__stdcall(stackId*, amount, map, apply)`, `ret 0x10`, пролог `mov eax, 0x6bce88` / `call 0x66bd10`. Вызовов у
него одиннадцать:

| Возврат | Откуда | `amount` | `cause` |
|---|---|---|---|
| `0x5d4470` | `0x5d41d8(map, playerId)` ← `CEffectRegenUnits::apply` `0x43b873`: начало хода, каждому отряду владельца (`+0x8c == player`) | `move − 0x5ed035(stack, map)` | `turn_start` |
| `0x43590c` | `CEffectChangeAP::apply` `0x4358d4` (строка `ap_apply` снаружи, `seq…seq_end`) | дельта эффекта | `ap_effect` |
| `0x439fc8` | `CEffectMove::apply` `0x439e84` | цена пути | `stack_move` |
| `0x437681` | `CEffectDropRod::apply` `0x437606` | весь запас | `rod_place` |
| `0x5d9ffb` | `0x5d9fab` ← `CEffectBreakRod::apply` `0x433c65` | весь запас | `rod_break` |
| `0x4398b4` | `CEffectModifier::apply` `0x439799`, только если `move > max` | `move − max` | `modifier_clamp` |
| `0x5d6e1a` | `0x5d6db7` ← `0x5d6cfb`, только если `move > max` | `move − max` | `clamp_max` |
| `0x5d6ee7` | `0x5d6e21` — выбор навыка лидера | `move − max` | `skill_pick` |
| `0x42f0f0` | `0x42f036` ← `0x4228e5` (сразу после открытия сценария `0x422b4e`) | `move − max` | `game_start` |
| `0x43089c` | `0x430798` ← `0x43002c`: цикл по всем отрядам | `move − max` | `stacks_init` |
| `0x42eb44` | `0x42eb1d` ← `0x41e507` ← `0x45149a` (разбор команды, не опознан) | `9999` — обнуление | `zero_9999` |

`0x5ed035` — `__thiscall(stack, map)`, `ret 4`: `MOVE` лидера через `0x5ea4dd` → `0x40a41f` → слот `+4`; **0**, если
`leaderId` пуст или юнит не найден. Байт «лидер жив» (`+0x2c`) ни `0x5ed035`, ни `apply` не читают. В начале хода при
мёртвом лидере `0x5d41d8` сначала обходит слоты (`0x5d4402…0x5d4450`), затем восстанавливает запас так же.
Бунт в деревне обнуляет запас отдельно: `ap_effect cause riot_turn_start` (`0x4441c8`) → `ap_apply` → внутри строка
`ap_restore cause ap_effect`.

|---|---|---|---|
| `ap_restore` | `stack`, `player`, `amount`, `move_before`, `move_after`, `max`, `leader`, `leader_found`, `leader_alive`, `zero`, `cause`, `ret_addr`, `ret`, `seq_end` | string×2, int64×4, string, bool, bool?, string?, string×2, bool, int64 | **Каждый вызов** `0x5e780d`, без ключа и бюджета: строка на отряд в начале каждого хода плюс по строке на ход по карте, жезл, эффект хода. Ключ здесь не годится: вопрос как раз «что стало с **этим** отрядом **в этот** ход», а сочетание (отряд, причина, числа) повторяется изо дня в день, и первая строка спрятала бы следующие. `stack` — аргумент; `player` — `ownerId` отряда после вызова; `amount` — аргумент (запас уменьшается на него, положительный — трата); `move_before`/`move_after` — `movement` до и после; `max` — `0x5ed035` после вызова; `leader` — `leaderId`; `leader_found` — юнит лидера найден на карте; `leader_alive` — байт `+0x2c`; `zero` — почему `move_after = 0`: `max0_no_leader` (`max = 0`, юнита лидера нет), `max0` (`max = 0`, лидер есть — его `MOVE` с модификаторами ноль), `spent` (`max > 0`, списано), `unknown` (`max` не прочитан); `null`, если запас не ноль. Отряд не прочитан — `player`/`leader` `"null"`, числа `−1`, `leader_alive` и `zero` — `null`. `cause` — по адресу возврата (таблица выше), иначе `unknown`. **Как искать обнуление.** Отряд с `MOVE 0` после смены хода: строка `ap_restore` с этим `stack` и
`cause = turn_start`. Нет её — отряд не прошёл цикл `0x5d41d8` (владелец не тот `player`); есть с
`move_after = 0` — причину называет `zero`; есть с `move_after > 0` — обнулил кто-то позже: следующая строка этого
`stack`, её `cause`.

## Схема 6.4: ход ИИ на карте (`ai_*`)

**Броски.** Строка `rng` вне боя не пишется, поэтому значения бросков берутся из кольца последних четырёх

`rng_after` — `rngCount()` до и после вызова.

**Чей ход.** У части функций нет аргумента «кто»: `turn_player` (и `player` у `ai_strategic_step`) — игрок, чей ход

идут и в чужой ход — там это поле называет не того игрока.

## Схема 6.5: экономика и тактика ИИ (`ai_*`, `crt_rand`)

Появилась 17.09.2026, живёт в `tools/d2probe/mss32/src/probeaieco.cpp` (`hooks::addAiEcoHooks`) и
`probeaitac.cpp` (`hooks::addAiTacticHooks`), помощники — `include/probeaiutil.h`. Разбор кода —
`disciples-modding/docs/synthetic-maps/analysis/O-re65-strategic.md` (экономика) и `N-re65-tactics.md` (тактика).
Адреса — `game-pristine/Discipl2.exe` (GOG 3.01, побайтно равен `game-dev`), capstone: пролог не короче 5 байт без
переходов и `ret`, переходов внутрь пролога нет (единственная находка сырого скана `0x466373` — середина
`push [ebp+0x14]`), ширина `ret` равна числу аргументов, `ecx` как `this` там, где заявлен (у `0x44dcb8` и `0x44dd87`
`ecx` уходит неявно в `0x56aff7` / `0x44df02`), адреса возврата `ai_eval` — `call + 5`. Прологи вида
`mov eax, imm; call 0x66bd10` (SEH-кадр) переносятся Detours так же, как у `0x448aad`. Все хуки только читают; зонд
сам зовёт лишь геттеры (слоты vftable, чей адрес лежит в коде exe), поиск `0x5f0560`, `findScenarioObjectById` +
`__RTDynamicCast` `0x66bda6` и проверки клетки `0x5d9bdb`, `0x5d9d1d`, `0x5cd11f` — те же вызовы, что делает сама
функция.

**Общие поля.** `player` — игрок, чей ход ИИ начался последним (как `turn_player` схемы 6.4, `null` — хода ИИ ещё не

`ptr`, `fn`, `p1`… — адреса строкой `"0x…"`. Дробные — JSON-числа (`null` — не прочитано или не конечно).

**Объект стратегии** (`eval` у `ai_eval`, `action` у `ai_candidate`/`ai_exec`) — `{"vft","class","type",поля…,"raw"}`:
класс и тип — по таблице vftable зонда, поля — по разбору (ранг 2/3, имя = вид + смещение: `id4` — id по `+4`,

(`0x429db7`–`0x429de7`). «Пересев» кладут строители сервера `0x403479` (новая игра) и `0x403540` (загрузка) через

`random` включён: загрузка **не восстанавливает** генератор из сохранения, он продолжает состояние процесса (предыдущей
партии), а записанное в файл пропадает. Порту: при «Random» после загрузки генератор — не из `.sg`; для харнесса — из
строки `rng_state what=load` (`index`, `table`, `n`). При выключенном «Random» новая игра не пересевает, а загрузка
восстанавливает (`rng_seed cause=load_save`, затем `rng_state` с `saved_same = true`).

**Почему это закроет расхождения.**
- *Торговец/маг/тренер дней 1–4* (`ai-tactic-candidates.md` §25): `ai_place_cache enter` даёт кошелёк сразу после заполнения и
  казну игрока в тот же момент (доход до/после), `cache` — есть ли площадки в сборе, что их выбросило (радиус главного отряда,
  исключения, три ближайших) и какой кошелёк видят построители. Если места `picked` и кошелёк не меньше цены, а кандидатов всё
  равно нет, — отказ в самом построителе (дальше — хук на `0x46aece`/`0x46a125`/`0x46ccef`).
- *Кэш крепостей* (legions `FT0006` с гостем `KC0060`): `ai_fort_cache` показывает по каждой крепости ответ фильтра, охраны, радиус
  и исключения — какая из пяти причин держит крепость вне кэша.
- *Своя сила B* (13/14/15 окон, §26): вклад каждого юнита с его здоровьем и цепочкой модификаторов — сверка `AiStrength` порта по
  юнитам, а не суммой (Banner Bearer у лидера с 1 HP, Unholy Chalice в столице).
- *Регенерация* (`UN001a` 111 против 100): каждое слагаемое лечения со своим процентом и хозяином группы — видно, какое слагаемое
  порт даёт лишним.
- *Цель повышения* (`UN0019`, `UN0014` в гарнизоне деревни): `target` null и запросы по пути — на каком шаге движок отказывает.
- *Равноценные пути* (`KC0085` д. 25, `KC0091` д. 40): порядок снятия узлов с `g`/`f` — правило выбора при равной оценке (куча
  Dinkumware), сверка A* порта узел в узел.
- *Порядок id* (найм, призыв, новые отряды): тип, выданный id и счётчик с вызывающим — порт повторит счётчики движка.

**Объём.** По партии ai-q09 (20 дней, `corpus/20260928-shots/passive-002.jsonl`, 40 МБ): оценок отряда ~1 000, пересборок кэша
столько же — `ai_place_cache` + `ai_fort_cache` ≈ 1–2 КБ на пересборку (≈ 2–3 МБ); `ai_strength_units` ≈ 0,4 КБ на вызов, шесть
на оценку атаки (≈ 3–4 МБ); `path_expand` — 300 узлов потолок, обычно десятки (≈ 5–8 МБ); `regen`, `upgrade_target`, `id_alloc` —
сотни килобайт. Итого +10–15 МБ за 20 дней, за 30 дней — до ~25 МБ. Бюджета «первые N» нет (правило проекта), только потолки
внутри строки: 300 узлов, 200 точек пути, 16 модификаторов, 256 записей дерева.

## Схема 7.4: ключи по видам и сброс при входе в партию (17.10)

`tools/d2probe/mss32/src/probe.cpp` (`emitKeyed`, `resetKeys`), вызов — `probeui.cpp` (хук `game_enter`, сразу после строки
`game_phase`). Новых строк нет; в `start` — `"schema":"7.4"`, в `counts` — поля `keys_dropped_by` и `keys_resets` (разбор —
`CountsEvent.KeysDropped`, `KeysDroppedBy`, `KeysResets`; у журналов до 7.4 — `null` и 0). Почему и как проверено — `docs/probe-av.md`,
раздел 6.

- **Свой потолок у каждого вида.** До 7.4 ключи всех видов лежали в одном множестве с потолком 200 000 на весь прогон; в
  `corpus/20261016e-av` его к середине карты 5 заняли ключи `move_cost`, и на картах 6–7 проверок (`*_check`) нет вовсе. Теперь
  `move_cost` — 200 000, прочие виды — по 20 000 своих ключей. **Схема 7.5:** ключ хранится 64-битным хешем FNV-1a (узел ~32 байта
  вместо ~120 у строки), потолок `move_cost` — 1 000 000 при прежней памяти (карта 10 `corpus/20261017-port-synth` дала 155 005 за карту);
  совпадение хешей двух разных ключей — порядка 1e-7 за прогон (одна непоказанная строка).
- **Сброс при входе в партию.** Каждая строка `game_phase` с `what` = `new`/`load`/`enter` (конструктор `CPhaseGame`) — граница:
  ключи всех видов забываются, и сочетание, уже записанное на прошлой карте (или до загрузки сохранения), пишется снова. Поэтому
  «число строк вида = число уникальных сочетаний» верно **внутри загрузки** (между строками `game_phase`), а не во всём журнале.
  Счётчики `calls`, `keys_dropped`, `keys_dropped_by` не сбрасываются — они за весь прогон. Если хук `game_enter` погашен
  (`probe/hooks.txt`), сброса нет (`keys_resets` = 0), свои потолки видов остаются.

## Схема 7.5: все броски решений игры вне показа и боя (`ai_rng`, 18.10)

## Журнал ввода

Появился в версии 5, живёт в `tools/d2probe/mss32/src/probeinput.cpp`. Цель — соотнести
действия игрока с событиями движка и с файлами сохранений, когда прогон играется руками.

| `ev` | Поля сверх общих | Типы | Точка | Пишется |
|---|---|---|---|---|
| `input` | `kind`, `msg`, `vk`, `button`, `x`, `y`, `sx`, `sy` | string, int64×7 | `PeekMessageA` / `GetMessageA` (экспорты `user32.dll`) | **Только на нажатие.** `kind`: `down` (кнопка мыши), `dblclk`, `wheel`, `key`. `msg` — номер оконного сообщения. `vk` — виртуальный код клавиши (только при `kind = "key"`, иначе `-1`). `button` — 1 левая, 2 правая, 3 средняя, 4 боковая; `-1` для клавиатуры. `x`/`y` — курсор в клиентских координатах окна, `sx`/`sy` — он же в экранных (`MSG::pt`). Когда окно не определилось, `x`/`y` равны `-1`, а `sx`/`sy` есть всегда. |

Почему насос сообщений, а не оконная процедура: `PeekMessageA`/`GetMessageA` — обычные
экспорты `user32.dll`, их адреса верны для любой сборки игры и не требуют реверса вовсе,
а через них проходит каждое сообщение, на которое игра реагирует.

Флуда нет по построению: строка пишется только на нажатие кнопки или клавиши (плюс
колесо), **никогда** на движение мыши и никогда на автоповтор клавиши (бит 30 `lParam`).
У `PeekMessageA` учитывается только вызов с `PM_REMOVE`: при `PM_NOREMOVE` одно и то же
сообщение возвращается снова и снова, и одно нажатие дало бы серию одинаковых строк.

**Клетка карты под курсором намеренно не вычисляется.** Движок и так публикует её в
событии `path` при каждом наведении (`end_x`/`end_y`), поэтому ближайшая предшествующая
строка `path` отвечает на этот вопрос без собственного пересчёта «экран → клетка».

Счётчик без бюджета для этого хука — **`counts.input_pump`**: сколько раз насос вообще
вызвался. Он и отличает «игрок ничего не нажал» (`calls.input = 0`, `input_pump` велик) от
«игра не зовёт функцию, которую мы перехватили» (`input_pump = 0`). Считается атомарно, без
замка и без выделения памяти: насос — самый горячий путь в игре, и обычный `countCall()` с
мьютексом и поиском по карте стоял бы прямо в нём. Имена хуков в `start.hooks` —
`input` (`PeekMessageA`) и `input_get` (`GetMessageA`).

## Индекс генератора (`rng_index`)

Реверс — `docs/re-rng.md` в `disciples-modding`, модель — `tools/re/rng.py` там же
(портирована в этот репозиторий как `tools/d2probe/tests/rng_model.py`, см. ниже).
Формулой одной строкой: `table[i] ^= table[i - 147 mod 250]; i = (i + 1) mod 250` над
константной таблицей 250 16-битных слов по `0x7b4978`; `rng_index` — это `i` (адрес
`0x838c24`) в момент записи строки. **Поправка схемы 6.2:** таблица меняется каждым шагом
(`table[i] ^= …`), `reseed` зовётся не один раз за процесс (новая игра, таймер интерфейса), а
загрузка сохранения записывает таблицу целиком — поэтому одного индекса недостаточно; состояние
после каждой такой записи — строка `rng_seed` (раздел «Схема 6.2»). Читается прямым
volatile-чтением памяти, без захвата критической секции `0x836fd8` — бой идёт в главном
потоке движка, гонок нет. Поле пишется только на сборке `Gog`; для `Akella`/`Russobit`/
`ScenarioEditor`/`Unknown` адрес не подтверждён реверсом, и поле в строке просто
отсутствует (не `null` — ключа нет вовсе).

## Идентификация нового/законченного боя

«Новый бой» — вызов `battleTurn` с другим `BattleMsgData`, чем у боя, уже давшего
`battle_start`; сбрасывается конструктором `BattleMsgData` (`0x62c920`), не самим
`battle_end` (доигровка лекарями после конца боя не должна читаться как второй бой).
Повторный `battle_end` для того же боя не пишется — движок зовёт
`updateGroupsIfBattleIsOver` не один раз.

## Проверка журнала

Две ступени, обе используются на образце в этой задаче:

```
python tools/d2probe/tests/probe_json_check.py <журнал.jsonl>
python tools/d2probe/tests/probe_invariants.py <журнал.jsonl>
```

`probe_json_check.py` — валидность JSONL, обязательные списочные поля у снимков боя,
уникальность `seq`, отсутствие `\r`. Разрывы `seq` там штатны: номер берёт каждый
хук, а `rng`/`rng_std` вне боя намеренно не журналируются. `probe_invariants.py` —
восемь проверок формы боя (парность `battle_start`/`battle_end`,
`miss.rng_after >= rng_before`, рост HP между `turn_before`/`turn_after`, `order` в
четырёх событиях — без повторов, целиком из `units` и **не пустой везде**,
`miss <= power`, безусловные итоги по `ev`, и информационная проверка [8]:
если в файле есть `rng` с `rng_index`, модель R250 (`tools/d2probe/tests/rng_model.py`)
воспроизводит по индексу первого броска пары `r` следующего для каждой смежной пары
`rng` по `n` — печатает `reproduced=K/N`); код выхода 1 только на невалидном JSON,
неверной паре `battle_start`/`battle_end`, битом `order` и на `order`, пустом во всех
событиях сразу — проверка [8] на код выхода не влияет. Остальное информационно.
Подробности — `tools/d2probe/README.md`.
