# Карта: неподвижные объекты, слои и порядок отрисовки

Разбор `Discipl2.exe` (GOG 3.01, `game-pristine`) дизассемблером capstone, 19.09.2026. Игра не
запускалась: всё ниже взято из кода и данных архивов. «Дизасм» значит, что место сверено с машинным кодом GOG по
адресу. «Тулсет» значит, что вывод опирается на `tools/d2probe/mss32/include` и `src`. Землю не повторяю, она
описана в `docs/ground-render.md`. Отряды, туман и метки описаны в `docs/map-render-stacks.md`: этот документ с
ним сверен, точка привязки и ключ сортировки у обоих одни и те же.

## Коротко

- **Все картинки карты кладутся одним правилом** (`0x5406d6` → `0x545b22`). Центр холста кадра совпадает с центром
  следа объекта. Холст кадра — это ровно PNG порта. Смещений внутри кадра движок не знает: куски уже разложены по
  холсту в `-IMAGES.OPT`, а порт их запёк.
- **Якорь элемента** `sx×sy` клеток с углом `(x, y)` (`0x5ac99c`, `0x5acb3d`): `ax = x + ⌊sx/2⌋ − [sx чётн.]`,
  `ay = y + ⌊sy/2⌋`, `dx = 32·[sx чётн.]`, `dy = 0`. Левый верхний угол PNG `W×H` в мировых пикселях:
  `P = ((ax−ay)·32 + 32 − ⌊W/2⌋ + dx, (ax+ay)·16 + 16 − ⌊H/2⌋)`.
  Для квадратного следа `s×s` это **`P = ((x−y)·32 + 32 − ⌊W/2⌋, (x+y)·16 + 16·s − ⌊H/2⌋)`**. Для холста 320×320:
  `P = ((x−y)·32 − 128, (x+y)·16 + 16·s − 160)`.
- **Размеры следа** (дизасм, конструкторы): столица 5×5, город 4×4, руины и лавки 3×3, кристалл, мешок, жезл,
  могила и дорога 1×1, ориентир — `CX×CY` из `GLmark.dbf`, горы — `SIZE_X×SIZE_Y` из `.sg` (1, 2, 3, 5). У
  локации след 1×1 в её центральной клетке, круг берётся по радиусу. Позиция объекта в `.sg` — верхний угол
  следа, то есть клетка с наименьшими `x` и `y`.
- **Порядок.** Сначала рисуется земля, затем все картинки карты одним списком по ключу
  `K = ((L>>9)·256 + ax + ay)·512 + L` (`0x545a58`), по возрастанию. `L` — номер слоя из `ImgData/IIsoLay.dbf`.
  При равном `K` порядок идёт по `P.y`, затем по `P.x` (`0x66e90f`). Значит, сортируется **диагональ якоря**
  (средняя диагональ следа), а не нижний угол. Слой — второй ключ, и в пределах одной «полосы» `L>>9` он
  работает только внутри диагонали.
- **Имена картинок** собирает движок, таблицы имён в данных нет. Архивы: IsoCmon (всегда), плюс IsoAnim (при
  `AnimatedIso`) или IsoStill (без него). Деревья, горы и дороги берутся из IsoTerrn. City.ff и Capital.ff на
  карте не используются. Имя должно найтись ровно в одном экземпляре, иначе картинки нет.
- **Анимации**: один кадр за тик группы 66 мс (`0x42`, `0x51d871`). Начальный кадр случаен.
- **Прозрачность кадра** (`opacity` в `-IMAGES.OPT`): 255 — обычный кадр, 128 — тени `…S` (полупрозрачные),
  300 — `OBJECTIVE*` и эффекты. Сборщик PNG это поле **игнорирует** (см. «Не закрыто»).

## 1. Как строится картинка элемента

`0x5ac803` для каждого элемента карты:

1. Собирает список пар «картинка, слой» (`0x5bb72c`). Обработчик выбирается по RTTI-типу элемента.
2. Каждую пару выводит `0x5aca58`: якорь по `0x5ac99c`, сдвиг по `0x5acb3d`. Картинка оборачивается в
   `CFogImage` (скрытие под туманом), затем `ShowImageOnMap(якорь, слой, картинка, dx, 0)`.
3. На одну пару «якорь, слой» приходится одна картинка. Новая заменяет старую.

**Поиск по имени** (`0x5c723b`). Имя ищется в двух хранилищах: IsoCmon и IsoAnim (при `AnimatedIso`) или IsoStill
(без него). Совпадение — по префиксу без учёта регистра, длина имени в заданном диапазоне. У всех имён ниже
длина равна длине образца, то есть совпадение точное. Исключение — дороги. Если найдено не ровно одно имя,
картинки нет. Найденное в IsoCmon грузится из IsoCmon, иначе из IsoAnim или IsoStill. В описи порта
(`data/gfx/*.json`) имя может оказаться и в `images`, и в `anims`: однокадровые анимации лежат в `anims`.

**Расы в именах.** Двухбуквенный код (`0x5c2ffb`, `0x5c70be`): Империя `HU`, Кланы `DW`, Легионы `HE`, Орды
нежити `UN`, нейтралы `NE`, эльфы `EL`. Там, где нужен `RACE_ID` из `Grace.dbf` (флаг, щит, жезл):
`G000RR0000` — Империя, `0001` — Кланы, `0002` — Легионы, `0003` — Орды нежити, `0004` — нейтралы, `0005` —
эльфы.

Уточнения по коду:

- **Лес** рисуется из `0x5ac20d` при пересчёте клетки, отдельно от элементов. Клетка-лес получает одну картинку
  дерева на слое `TREES` с якорем в самой клетке. Проверка по 33 картам `Exports` подтверждает поля:
  `B` = 0..23 у `HU` и `EL`, 0..22 у `DW` и `HE`, 0..24 у `UN`, 0..18 у `NE`. Это ровно число файлов `…F00vv`, у
  `NEF` запасной `0019`. `A` везде 0. Код расы клетки: 1 `HU`, 2 `DW`, 3 `HE`, 4 `UN`, 5 `NE`, 6 `EL`
  (`Lterrain.dbf`, таблица `0x5a5f8a`).
- **Горы** — отдельный объект: список записей `CMidMountains` (`ID_MOUNT`, `SIZE`, `POS`, `IMAGE`, `RACE`), в
  памяти `+0` позиция, `+8` размер, `+0x10` картинка, `+0x14` раса. Имя без расы (`MOM0100`…) и `MOM_DW0502`
  движок не запрашивает. Грунт «горы» в клетке даёт только узор `NE` земли (см. `ground-render.md`).
- **Ориентир** на слое `LMARK_GROUND` не рисуется никогда. Проверка `0x5ee07b` всегда возвращает 0, так что
  ветка мёртвая.
- **Анимация или статика.** При `AnimatedIso` берётся IsoAnim, иначе IsoStill. Что лежит в IsoCmon, одинаково в
  обоих режимах. Флаг `0x838524` передаётся в сборщик (`0x5ac8bc`). В `Disciple.ini` есть `AnimatedIso=1` (поле
  настроек `+0x180`), но запись флага из настроек не прослежена.
- **Значки** `RUIN_ICON_*` / `SITE_ICON_*` рисуются только при одном из флагов `0x838650` / `0x838651`. Их
  переключает интерфейс карты (`0x489084`, `0x48d377`, `0x490a15`); какая это кнопка, спросить у пользователя.
- `G000SI0000MERH00S` (тень лавки) в архивах есть, но обработчик лавок тень не запрашивает.

## 3. Точка привязки и PNG порта

```text
якорь (0x5ac99c):  ax = x + sx/2 − (sx чётн. ? 1 : 0),   ay = y + sy/2      # деление целое
сдвиг (0x5acb3d):  dx = sx чётн. ? 32 : 0,               dy = 0
угол  (0x545b22):  X = (ax − ay)·32 + 32 + W/(−2) + dx,  Y = (ax + ay)·16 + 16 + H/(−2)
```

`W×H` — `getSize` картинки. У неподвижной (`0x52da58`) это размер записи кадра, у анимации (`0x52dfa0`) — размер
текущего кадра, а у всех кадров одной анимации в архивах он одинаков (проверено по всем PNG IsoAnim, IsoCmon и
IsoStill). Этот размер — холст кадра из `-IMAGES.OPT`, то есть ровно PNG порта (`ff_extract.build_frame`).
Поля смещения у кадра нет. **PNG кладётся левым верхним углом в `P = (X, Y)` без поправок.**

Итог — центр PNG ставится в центр следа `((x−y)·32 + 32, (x+y)·16 + 16·s)`. Для чётного `s` это тоже верно:
якорь сдвинут на клетку влево-вниз, а `dx = 32` возвращает центр.

Проверка по данным: содержимое кадров привязано к центру холста, а не к своему прямоугольнику.

| кадр | холст | нижний край содержимого от центра | нижний угол следа от центра |
|---|---|---|---|
| столица `HU0` / `UN0` / `DW0` (5×5) | 320×320 | +91 / +85 / +88 | +80 |
| город `NE1`…`NE5` (4×4) | 320×320 | +43…+66 | +64 |
| гора `MOMNE05vv` (5×5) | 320×320 | +89…+92 | +80 |
| гора `MOMNE01vv` (1×1), дерево `HUF0000` | 320×320 | +19, +15 | +16 |
| мешок на суше / сундук в воде | 100×100 / 320×320 | +13 / +4 | +16 |
| `LOCATION3` | 186×96 | ромб ±93, ±48 | ровно ромб 3×3 |

Если бы движок центрировал прямоугольник содержимого, столица `HU0` (содержимое −160…+91) опустилась бы на
34 px ниже следа. Кристаллы с разными холстами (`G000CR0000WH`: 62×72 в IsoStill и 320×320 в IsoAnim) при
центрировании холстов совпадают с точностью до кадра анимации.

Готовые формулы для 320×320: 1×1 — `((x−y)·32 − 128, (x+y)·16 − 144)`, 3×3 — `(…, (x+y)·16 − 112)`,
4×4 — `(…, (x+y)·16 − 96)`, 5×5 — `(…, (x+y)·16 − 80)`. Дорога (62×32): `((x−y)·32 + 1, (x+y)·16)`, как
туман (см. `map-render-stacks.md`).

## 4. Порядок слоёв и сортировка

**Кадр** (`C2DEngine::draw` `0x66c6ab`): сначала дочерние элементы движка (`0x5304bd`), затем список картинок
карты (`0x66c399`). Земля — отдельный движок `CIsoEngineGround` с собственным `render`. Её непрозрачные ромбы
лежат под всем остальным. Что она рисуется первой, следует из устройства, но регистрация земли ребёнком
`C2DEngine` не прослежена.

**Список картинок** (`C2DEngineMapImpl`) — вектор корзин, упорядоченных по `K` (двоичный поиск `0x66e986`).
Внутри корзины картинки упорядочены по `(P.y, P.x)` (`0x66e90f`). Обход при отрисовке прямой (`0x66cb4b`), с
отсечением по экрану.

```text
K = ((L >> 9)·256 + ax + ay)·512 + L        # 0x545a58; K ≤ 0 не добавляется (0x66c91c)
```

Полосы `L>>9` и слои (`NUM` из `ImgData/IIsoLay.dbf`):

| полоса | слои по возрастанию `L` |
|---|---|

Жирным выделены слои этого документа, курсивом — отряды (`map-render-stacks.md`).

Что из этого следует:

- **Главный ключ — диагональ якоря `ax + ay`.** Для квадратного следа `s×s` она равна `x + y + s − 1`, то есть
  средней диагонали следа. Объект с меньшей диагональю рисуется раньше, какой бы ни был слой. Дорога
  диагонали `d` ляжет поверх дерева диагонали `d − 1`, если их картинки пересекаются. Отряд на диагонали
  `d + 1` перед столицей рисуется поверх неё, а отряд на передних клетках следа с диагональю меньше средней
  оказывается под ней. Так в оригинале.
- **На одной диагонали** порядок задаёт слой. Дорога и тени идут вниз. Затем деревья (388), могилы (389), путь
  (390), отряды (391), горы (392), мешки, ориентиры, лавки, руины, жезлы, кристаллы. Выше всех — города, бунт,
  флаги, столицы, щиты (413–420).
- **При одном слое и одной диагонали** порядок задают `P.y`, затем `P.x`. У одинаковых холстов на одной
  диагонали `P.y` совпадает, и левый рисуется раньше.
- Полосы 1–3 добавляют к диагонали 256, 512 и 768. Значки над лавками и руинами (870) поэтому рисуются поверх
  всех объектов полосы 0, `LOCATIONS_TOP` и туман — ещё выше.
- **Особенность оригинала:** на диагональ отведено 8 бит. На карте 144×144 диагональ `x + y ≥ 256` переходит в
  следующую полосу (подробнее — в `map-render-stacks.md` §3).

**Для порта**: одно дерево сортировки с ключом `(K, P.y, P.x)` по возрастанию, земля под ним. Слои Godot
(`z_index`) повторяют это только при полосах. Порядок внутри полосы 0 держится на диагонали, и одним
`z_index` на слой его не выразить.

## 5. Анимация и прозрачность

- `FactoryImageAnim` регистрируется в аниматоре (`0x52def1` → `CRendererImpl` `+0xc`, vtable `0x6e04b4` `+0` =
  `0x518fc0`) в группу 0. Группа 0 создаётся с периодом `0x42` = 66 (`0x51d871`), группа 1 — с `0x21` = 33
  (быстрая, для `CTwoSpeedAnimator`). Тик (`0x51e0d0`): если `now ≥ next`, каждая анимация группы делает
  **+1 кадр** по кругу (`0x52dfdd`), затем `next = now + 66`. Пропущенные тики не догоняются. Единица часов
  (`0x5613e1`) по смыслу — миллисекунды, источник не прослежен. **Итого около 66 мс на кадр (≈15 кадров/с) у
  всех анимаций карты.** Отряды — см. ниже.
- **Две группы (`CTwoSpeedAnimator`, разбор 16.10).** Система анимаций карты (`CMidAnim2System::Impl`, `0x40ab78`) держит два
  `CTwoSpeedAnimator` (`0x40ac86`: слот 1 аниматора — быстрая группа, 0 — медленная) и на тике группы шагает текущую задачу только если её
  байт группы (`0x4f11dc`, `[[задача+4]]`) совпал с флагом тика (`0x40ae5f`). Байт ставит `CMidAnim2Base` (`0x4f1137`): `CMidAnimSmoothScroll`
  — 1 (`0x4f4920`), `CMidAnim2Unit` (ход отряда) — `StackSmoothScroll` (`0x4f5e7c`), остальные задачи (`Appear`, `ChangeFog`, `Map`/`Terrain`,
  `Shake`, `Sound`, `TakeBag`, `LootRuin`, `CityGrow` и наследники `CMidAnim2Animation` — литьё, гибель, создание, смена владельца, горы, начало
  боя) — 0. Прочие пользователи быстрой группы — чат (`0x487093`), титры (`0x4db0f7`), прокрутка текста (`0x533dbb`); объекты карты, вода,
  облака, курсоры, бой (`CBatUnitAnim`) — медленная. Порт: `D2.Data.Map.AnimClock`, `AnimTicker`.
- Начальный кадр случаен: загрузчик (`0x5ae0bf`, флаг `1` у всех объектов) ставит `R250(n)`. Деревья, горы и
  дороги грузятся без случайного кадра, но они и не анимированы.
- Перерисовка объекта фазу не сбивает (`0x5ace8a` → `0x5bbecf`: кадр старой картинки), нетронутые объекты движок не перерисовывает вовсе.
  Порт (11.10, замечание п. 22 «мигает вся карта в ход ИИ»): `MapObjects.Build` оставляет переиспользованному узлу его кадр; прежде каждая
  пересборка (в ход ИИ — на каждой заявке) возвращала все анимации карты к кадрам `Random(1)` — на дне 30 human это 4256 скачков кадра за
  ход ИИ из 39 пересборок. Куски земли при обновлении тумана держат старую картинку до новой (`MapView._stale`), без дыр на время сборки.
- `opacity` в записи кадра `-IMAGES.OPT`: 255 у всех обычных кадров, 128 у теней `G000FT0000NE2S` и
  `G000SI0000MERH00S` (все кадры), 300 у `OBJECTIVES.PNG`, `RMVMOUNTAIN*`, `G000UU999*` и `SPELLAREAFOG`. У
  `OBJECTIVE*` фон чёрный и в PNG порта непрозрачный, так что 300 — по всей видимости, сложение цветов. Режим
  в коде не разобран.

## 5а. Смена тумана кольцами (`CMidAnim2ChangeFog`, разбор 16.10)

Команду `CCmdChangeFogMsg` (клетка `+0x10`, «закрыть» `+0x18`, прямоугольник `+0x1c`, радиус `+0x2c`; конструктор `0x47aebb`) шлёт только
`CEffectFog::apply` (`0x438314`), если эффект не «тихий» (`+0x19`); эффект создают развеивание (`0x41c723`) и туман (`0x41c7f8`) заклинанием,
призыв (`0x41c323`), смена владельца (`0x4366e2`), `L_CREATE_STACK` (`0x43bd74`) и `L_UNFOG` (`0x43d7c4`). Прямоугольник — клетка
`(x, y)…(x + 1, y + 1)` (`0x438462`), радиус — тот же, на который модель меняет туман (`0x5d5230`). Клиент (`0x4f351d`): прокрутка к клетке
(только если далеко, без проверки видимости), затем задача `0x4f1a29` в медленной группе:

- прямоугольник шире на радиус и зажат в `[0, размер]`; сторона `s`, центр `((л + п) >> 1, (в + н) >> 1)`, кольцо 1;
- старт (`0x4f1d16`) — при закрытии сначала `0x4f1d39` (не разобран), затем сразу шаг; шаг (`0x4f1b63`, тик 66 мс): клетки периметра квадрата
  «кольцо × кольцо» от угла `(cx, cy)`, у кольца > 1 угловые — на клетку внутрь по диагонали; каждой клетке в карте — туман (`0x5f3bdc`),
  перерисовка её и 8 соседей (`0x5ac56a`); затем `cx − 1, cy − 1`, кольцо + 2; конец — на шаге, где `кольцо + 2 > s` (`0x4f1b9f`).
  Без прозрачности: клетка сменяется целиком. У незажатого квадрата — `r + 1` шагов (центр, кольца 1…r), тронуто — квадрат `±r` без углов
  (как форма эффекта); у края карты центр сдвинут, и часть клеток эффекта кольца не задевают.

Порт: `D2.Data.Map.FogReveal` (кольца), `MapView.Fog.cs` — вид показывает свой туман зрителя (`MapScene.Build(fog:)`), который догоняет
модель кольцами после литья развеивания/тумана (центр и радиус — как у модели), события `L_UNFOG` на пути человека и в ходе ИИ/начале хода
(центр и радиус — по рамке сменившихся клеток, ранг 3: откуда эффект, вид не знает); обзор по шагу хода, захват и прочее — сразу. Клетки,
не задетые кольцами у края, порт ставит в конце (у движка, вероятно, до следующей перерисовки; ранг 3). Проверка — `ui-render-check`
«смена тумана» (шаг `fogtest`: кольца по своему пересчёту, шаг ≥ 66 мс, расхождений с моделью после показа 0).

## Для порта

- Данные на входе: объекты `.sg` (позиция — угол следа, поля из таблицы §2), `GLmark.dbf` (`CX`, `CY`),
  `IIsoLay.dbf` (номера слоёв), биты 19–31 клеток `MidgardMapBlock` (деревья), `Disciple.ini` `AnimatedIso`.
- Имя → PNG через `GfxAssets` по паре «архив, имя». Порядок поиска: IsoCmon, затем IsoAnim или IsoStill. Имя
  ищется и в `images`, и в `anims`.
- Размещение: `P` из §3. Сортировка: `(K, P.y, P.x)` из §4. Анимация: 66 мс на кадр, случайный первый кадр.
- В опись `data/gfx` стоит добавить `opacity` кадра. Без него тень города и круг цели нарисуются неверно.

## Не закрыто

- Попиксельной сверки с кадром игры нет. Удобная проверка — город или столица рядом с отрядом и деревом на
  соседних диагоналях, с известной прокруткой.
- Режим смешения при `opacity` 300 (сложение?) и 128 (альфа 50 %?) в коде не найден. Нужен разбор
  отрисовщика кадра `ImgStore2` или снимок круга цели.
- Что земля рисуется до списка картинок, следует из устройства и непрозрачности земли. Сама регистрация
  `CIsoEngineGround` в `C2DEngine` не прослежена.
- Единица часов аниматора (`0x5613e1` → vtable `+0x38`) не проверена, 66 считается миллисекундами.
- Откуда берётся флаг `AnimatedIso` `0x838524`: пишет его `0x5ab29c`, вызывается по vtable. Связь с
  `Disciple.ini` предположена.
- Точные условия круга цели (`0x57f529`, проверка владельца и игрока) не разобраны. В таблице — упрощённо:
  «объект в списке целей».
- Размер следа ориентира `CX×CY` взят из `GLmark.dbf` и тулсета, запись в `CMidLandmark` не прослежена.
  Размер локации 1×1 взят из конструктора, при загрузке `.sg` он не проверялся.
- Флаг `LOCATIONS_TOP` `0x838894` и кнопки значков `0x838650` / `0x838651` — кто и когда их ставит, не
  выяснено (интерфейс знает пользователь).
- В `map-render-stacks.md` §3 якорь крупных элементов записан как `(x + ⌊W/2⌋ − 1, y + ⌊H/2⌋)`. Вычитание
  единицы и `dx = 32` там только при **чётной** ширине, при нечётной якорь `(x + ⌊W/2⌋, y + ⌊H/2⌋)`
  (`0x5ac9cc`: `dec ecx` только при нулевом остатке).
